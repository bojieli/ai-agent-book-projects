## 0. 为什么架构必须再改一版

故事集已经从「会后写纪要」扩成：

| 条线 | 执行故事 | 管理/分析故事 |
|------|----------|----------------|
| 研发 | R1–R4 | R5–R8 交付/资源/治理/优先级 |
| 业务 | B1–B3 | B4–B7 经营分析/额度建议/路线图/渠道 |
| HR | H1–H3 | H4–H6 招聘漏斗/减员分析/编制盘点 |
| 风控 | K1–K3 | K4–K6 限额/模型监控/欺诈专项 |
| 合规 | C1–C3 | C4–C6 制度/迎检/合作方 |
| 跨条线 | X1–X4 | 消歧后分系统写回 |

v6 架构若仍按「MinutesAgent + 通用 Todo」理解，会撑不住：

1. **工具会爆炸**——每条线一套管理系统，不能全塞进一次 LLM 调用（书 Ch4：工具过多伤害选型）  
2. **黑话会串味**——全行词表硬灌等于装懂（书 Ch2/Ch3：上下文与记忆必须受控）  
3. **权限会穿仓**——H5/K3/C1 与普通项目同步不是同一密级（书 Ch10-8：信息权限）  
4. **长任务会堵死对话**——转写 Map-Reduce、建单、回流与用户插话并存（书 Ch4-5 async-agent）  
5. **没有评测故事会漂移**——场景一多，Prompt 会偷偷改语义（书 Ch6）

所以 v7 把架构收成一句话：

> **用书里的 Harness / Skills / RAG 与分域记忆 / 事件异步 / 管理者多 Agent / 评测门禁，托住故事集里每一类「执行会 + 管理会」——而且会能「接着上次开」。**

**补丁说明（相对初版 v7 叙述）：**  
初版把 RAG 缩在 Domain Layer 的一行里，容易被理解成「可选 briefing」。不对。  
行内文档支撑与**跨会连续性**是主路径能力，见下文 **§2.4 Meeting Knowledge Plane（RAG）**。

### 2.1 双平面（直接来自 async-agent 实验直觉）

故事里真实发生的是：人还在企微里改参数，后台已经在跑转写理解；或者建单还没完，人问「进度如何」。

| 平面 | 干什么 | 紧急度（对照 Flux） |
|------|--------|---------------------|
| **Dialog Plane** | 预订、澄清、HITL 改参、问进度、取消任务 | IMMEDIATE / INTERRUPT |
| **Pipeline Plane** | Understanding → Artifacts → WorkEmbed → Sync | 长任务；完成以事件回灌 |
| **Presentation / Render** | 按 `acl_view` 渲染邮件/图表/HTML → Delivery | 可与回流并行；换模板不重跑理解 |

规则：

- 「取消这场会后处理」= INTERRUPT，停流水线并留痕  
- 「纪要出了吗」= IMMEDIATE，不取消流水线  
- 「出完再按新模板渲染」= DEFERRED，挂到流水线阶段点  

没有双平面，管理会（R5/B4）和长转写会把对话堵死——这正是实验 4-5 要避免的。

### 2.2 Scenario Skill Pack = 场景能力包（SOP **按需**，不是全场景标配）

**禁止**把 R1–C6 全部 Prompt/Schema/SOP 塞进 system。

**关键修正（v7.4）：不是每个会议场景都有行内 SOP。**  
同步会、排期对齐、一般需求过会、口径讨论等，常常只有「目的 + 产物期望 + 写回哪」，没有可执行的流程手册。架构必须诚实对待这一点——**禁止为凑「必做」去虚构一份假 SOP**。

因此 Skill Pack 分两档编排模式：

| 模式 | `orchestration_mode` | 何时用 | Pipeline 怎么走 |
|------|----------------------|--------|-----------------|
| **Formal SOP** | `sop` | 行内确有流程/检查单（发布、迎检整改、策略上线评审…），或故事本身就是强流程 | 按场景 `sop/steps.yaml` 确定性编排；validate Hook = 墙 |
| **Default Playbook** | `playbook` | **无场景 SOP**（多数日常会、`general` 降级、轻量同步） | 走平台统一 Default Playbook（retrieve→extract→artifact→schema_validate→hitl?→embed?→index）；**不假装有场景 SOP** |

```text
ScenarioProfile / Skill Pack 声明：
  orchestration_mode: sop | playbook
  # sop：必须有 steps.yaml + 至少一个 validate Hook
  # playbook：禁止空壳 sop/；依赖平台 Default Playbook + schemas + Policy
```

业界 Agent Skills 用三级渐进披露；纪要君同一思想，**SOP 层按需出现**：

| 层级 | 加载什么 | 何时 | 对照 |
|------|----------|------|------|
| L1 Catalog | name + description + 适用条线/禁忌摘要 + **orchestration_mode** | 会话开始 | Skills metadata |
| L2 Instructions | `SKILL.md`：目的、成功标准、产物列表、Policy 引用 | 场景激活 | Skills body |
| L3 Resources | schema、词表切片、检查清单、示例；**若 mode=sop 再加载步骤图** | 按需 `read` | Skills `references/` |
| L4 Scripts / Hooks | schema 校验、生产禁令；**mode=sop 时还有 checklist/validate** | validate / Evaluator 调用 | Harness Hooks 是墙 |

```text
skills/<org>/<story_id>/
  SKILL.md                 # L2（必有）；声明 orchestration_mode
  schemas/                 # L3 产物与 WorkObject（必有）
  sop/                     # 仅 mode=sop 时存在
    SOP.md
    steps.yaml             # 可执行步骤图：step / type / tools / hitl / next
    checklists/
  references/              # 指向 Knowledge 中的制度/规范 doc_id
  eval/                    # 本故事评测用例指针（必有）
```

**有 SOP 时：** SOP 不是散文纪要模板，而是可编排步骤图（模糊 SOP 先 Clarifier→结构化 Plan→再执行）：

```text
step_type:
  retrieve | extract | decide | validate | hitl | embed | index | render | notify
```

**无 SOP 时（Default Playbook）：**

```text
Understanding → retrieve(可选) → extract → Artifact(按 schema)
  → schema/Policy Hooks（生产禁令等仍是墙）
  → Evaluator（对照 Skill 成功标准 + schema，不是对照不存在的 SOP checklist）
  → HITL（playbook 模式默认更严，见下）
  → embed? → continuum_index → acl_view→render? → notify?
```

| 约束（playbook 模式） | 规则 |
|------------------------|------|
| 自动嵌入 | 默认 `embed_gate=confirm_only` 或 `block`；**不得**因「没写 SOP」就放宽 |
| 生产生效类写回 | **一律禁止**自动；必须升级为有 SOP 的场景或显式 HITL+Policy 放行 |
| 高敏（H5 等） | 可以没有「发布检查单式 SOP」，但 **critical Policy 模板仍必绑**；不是用 SOP 有无决定密级 |
| `general` 降级 | 固定 `playbook`；只产可读视图 + 待确认草稿；不写高风险系统 |

例子：

| 故事 | 模式 | 编排要点 |
|------|------|----------|
| R1 需求同步 | 常为 **playbook** | schema 抽行动项 → HITL → 任务系统；无发布级 checklist |
| R4 发布评审 | **sop** | 拉清单 → Continuum 条件 → Go/No-Go → **checklist Hook** → HITL → 变更系统 |
| K1 策略评审 | **sop** | 抽 Shadow/灰度建议 → **production_effect 禁令 Hook（禁止对生产生效）** → HITL → 草稿 |
| C2 整改推进 | **sop** | Continuum 未关闭项 → 完成须绑证据 citation |
| H5 减员分析 | **playbook + L2 + classification=critical + sealed** | 关键是 critical Policy（禁群发/宽检索），不凑假发布级 SOP |
| B4 经营复盘 | 常为 **playbook** | 对照上期 Continuum → 经营动作草稿 → 确认后写台账 |

Pipeline Plane：`mode=sop` 时按 `steps.yaml` 确定性编排；`mode=playbook` 时按平台 Default Playbook。两种模式下 LLM 都**不能跳过 Policy/生产禁令 Hook**。Hooks are walls, not suggestions。

Orchestrator 只先看 **L1 catalog**；激活后再 L2；需要字段/步骤再 L3——可装备上百个场景，其中只有一部分带 SOP。

跨条线会加载多个 pack 的 L1，并强制 **Disambiguation** 阶段（故事 X1–X4）。

### 2.3 PolicyEngine（Constrain 的独立所有者）

故事迫使策略从「Agent 自觉」升级为独立引擎：

| 策略维度 | 例子 |
|----------|------|
| classification | `public\|internal\|confidential\|critical`（**唯一密级字段**；旧文 `sensitivity=critical` ≡ `classification=critical`） |
| **embed_gate** | `allow` / `confirm_only` / `block` — **唯一运行时嵌入闸门** |
| production_effect | 业务额度建议、风控策略：**默认不可对生产生效** |
| delivery_scope | 最小必要；H5 禁止群发与宽检索 |
| glossary_scopes | 只允许本场词表桶 |
| knowledge_scopes | 允许检索的文档库/会议连续体范围 |
| continuum_write_class | 见 §2.4.7（宽索引 / 域内 / 密封 / 不入检） |
| tool_allowlist | 本 Skill 可发现的 Connector 集合 |

#### 2.3.1 embed 闸门：单一真相（废除双枚举）

**废止**把 `auto_embed_policy` 与 `embed_gate` 当两套并存语义。  
统一为：

```text
ScenarioProfile.default_embed_gate   # 场景静态默认：allow | confirm_only | block
PolicyEngine.embed_gate              # 本场会议运行时生效值（可审计快照进 policy_binding）
```

合并规则（硬）：

1. 运行时 `embed_gate = max_strict(场景默认, 密级模板, 消歧状态, 理解门槛, orchestration_mode 约束)`  
2. 严格度排序：`block` > `confirm_only` > `allow`  
3. 任一来源要求更严，取更严；**Agent 不可放宽**  
4. **每次收紧必须追加新的 `policy_binding` 版本**（不可改写旧版；详见 05）  
5. 旧名 `auto_embed_policy` 读作 `default_embed_gate` 别名（`never→block`，`after_hitl|after_owner_confirm→confirm_only`）  
6. `production_effect_cap`（策略上限）与 `work_object.production_effect`（实际等级）分离；实际不得超过 cap  

典型收紧：

| 条件 | 至少升到 |
|------|----------|
| `orchestration_mode=playbook` | `confirm_only`（不得因无 SOP 放宽） |
| 跨域消歧未完成 | `confirm_only`；生产生效类 → `block` |
| 理解不足 / 未知术语挡决策 | `block` 自动嵌入 |
| `classification=critical`（H5 等） | `confirm_only` 或分步确认；Delivery 默认 off |
| `production_effect` 写回 | 默认 `block`，除非 SOP+HITL+Policy 显式放行 |

PolicyEngine 在 ToolRuntime.Authorize **以及 RAG 检索/写入**之前生效；Agent 不能覆写。

### 2.4 Meeting Knowledge Plane（RAG 主路径，不是点缀）

**为什么必须一等公民**

1. **各场景都有行内文档支撑**：研发有设计/接口规范，业务有口径与活动案，HR 有制度，风控有策略说明，合规有制度与检查清单。没有文档 RAG，模型只能靠通识「猜」。  
2. **本次会往往接着上次开**：未关闭行动项、上次 Go/No-Go 条件、整改进度、经营动作是否落地——必须从**历史会议产物与 work_links**召回，而不是用户每次口述。  
3. 书 Ch3 的结论：长期能力在「可检索的外部化知识」，不是把所有历史塞进当前 context。

#### 2.4.1 两类语料（必须分开建索引、分开鉴权）

| 语料库 | 内容 | 典型用途 | 密级注意 |
|--------|------|----------|----------|
| **Enterprise Docs Corpus** | 制度、规范、设计文档、策略说明、FAQ、检查清单、口径辞典… | 会前准备、理解黑话/条款、产物引用依据 | 按 org_domain + 密级分库或过滤 |
| **Meeting Continuum Corpus** | 历史会议的结构化产物、决议、未决项、work_links 摘要、经授权的纪要视图 | 「接着上次开」、复盘对照、整改推进、交付周会 | **写入分级见 §2.4.7**；默认可检=结构化摘要+回链 |

术语 Cards 仍在 Domain Layer；RAG 负责**大块文档与跨会记忆**，两者互补：

```text
Cards（精、可执行）     RAG（广、可引用）
  灰度=发布|客群|策略       上次发布评审的条件项原文 span
  策略ID别名               策略变更说明文档章节
```

#### 2.4.2 检索管线（对照 Ch3 retrieval-pipeline）

```text
Query 构造（会议 purpose + 议程 + 参会域 + 关联 meeting_id/项目）
  → ACL / org_domain / classification 预过滤（先鉴权再检索）
  → Hybrid：Dense + Sparse（专有名词、制度文号靠 sparse）
  → Rerank
  → **必做** Contextual chunk prefix：带「所属制度/项目/会议」前缀  
  → **必做能力**：召回不足时 **bounded multi-hop rule rewrite**（硬限制轮次与预算；确定性，非 LLM Agentic）  
  → 注入 Context 尾部或 Artifact 的 references[]（带 citation）
```

铁律：

- **先 ACL 后检索**，禁止「先召回再删敏感」当唯一防线  
- 注入的是**摘录 + 来源 ID**，不是整本手册（Skills 渐进披露同一思想）  
- 转写/外部材料仍是不可信通道；文档摘录也不得直接变工具参数  

#### 2.4.3 何时召回（全生命周期，不是「可选 briefing」）

| 时机 | 召什么 | 故事例 |
|------|--------|--------|
| **会前 Dialog** | 相关行内文档 + **同项目/同主题历史会**未关闭项、上次决议 | R5 拉红灯里程碑；C2 拉整改台账；B4 拉上期经营动作 |
| **Understanding** | 术语难懂时查文档释义；歧义时查历史用法 | 「灰度」在本项目历史会里指什么 |
| **Artifact 生成** | 对照文档与上次结论，避免推翻未声明的既有决议 | R2 条件项是否已在上周评审出现 |
| **WorkEmbed 前** | 查是否已有同类工单/变更，防重复建单 | 幂等之外的「业务重复」 |
| **会后索引写回** | 本次结构化产物（及授权视图）写入 Continuum Corpus | 让「下次会」能召回这次 |

#### 2.4.4 跨会连续性对象（Continuum）

```text
MeetingThread / Series
  ├── series_id / project_id / topic_keys
  ├── prior_meeting_ids[]
  ├── open_artifacts[]      # 未关闭决策、条件项、整改、经营动作
  ├── open_work_links[]     # 未关闭外部工单
  └── last_resolved_citations[]
```

会前 Orchestrator 若识别到 `series_id` 或同一 `project_id`，**默认启用 Continuum 检索**，而不是等用户说「你看看上次纪要」。

#### 2.4.5 分条线文档举例（说明 RAG 覆盖面）

| 条线 | 行内文档例 | 历史会例 |
|------|------------|----------|
| eng | 接口规范、架构决策、发布清单 | 上次技术评审条件、故障改项是否关闭 |
| business | 口径辞典、活动方案 | 上期经营动作有没有执行 |
| hr | 制度、招聘流程（高敏） | 编制盘点结论；H5 默认不进宽检索 |
| risk | 策略说明、模型卡 | 上次 Shadow 观察结论、限额决议 |
| compliance | 制度库、检查要点 | 整改项跨会推进、口径版本 |

#### 2.4.6 Domain Cards 与 Knowledge Plane 的边界

| | Domain Cards | Meeting Knowledge Plane |
|--|--------------|-------------------------|
| 形态 | 短结构化 | 文档块 + 会议产物索引 |
| 主问题 | 「这个词在本域是什么意思」 | 「依据哪份文档/哪次会」 |
| 更新 | 术语确认回写 | 文档同步入库；会后产物索引 |

跨域同词异义：Cards 上多义项 + Continuum 里「本项目历史用法」检索，一起做消歧。

#### 2.4.7 Continuum / Docs **写入**策略（与检索对称，硬契约）

检索已要求「先 ACL 后召回」。写入必须同等硬，禁止「会后一律写宽索引」：

| `continuum_write_class` | 写入什么 | 谁能召回 | 典型故事 |
|-------------------------|----------|----------|----------|
| `wide` | 结构化摘要 + open 项 + work_links 回链 → **宽 Continuum 索引** | 同系列/项目且 ACL 通过的会 | R5、B4、多数 eng 执行会 |
| `domain` | 同上，但只进 **org_domain 域内索引** | 同域 + ACL | 一般 HR 制度会、风控内部复盘 |
| `sealed` | 仅脱敏结构化摘要（无点名清单/无原文）→ **密封库**；宽检索永远 miss | 显式授权的同系列极窄参与者 | H5、绩效校准片段、K3 案件 |
| `none` | **不入任何 Continuum 检索面**；仅对象存储 + 审计留痕（按 retention） | 无人经 RAG 召回 | 用户/Policy 明确禁止入检 |

硬规则：

1. `classification=critical` 默认至少 `sealed`；全文纪要 / 当事人清单 **禁止** `wide`。  
2. 会后「索引写回必做」= **必须执行写入决策**（写到哪一类），不是必须写入 `wide`。  
3. `retrieval_trace` 与 `continuum_write_receipt` 可审计：写了哪类、拒写原因。  
4. Eval 负例：H5 产物出现在无关会议的 Hybrid 召回里 = 门禁失败。

Docs Corpus 写入另遵文档治理（审批入库）；会议 Agent 默认 **只读 Docs**，不自动把转写升格为制度原文。

  → 写入本轮 tools 末尾（保持 system 静态前缀）

执行层与管理层 Connector 分开注册，例如：

| 域 | 执行 Connector 例 | 管理 Connector 例 |
|----|-------------------|-------------------|
| eng | 需求/缺陷/发布 | 交付看板/排期/治理/OKR |
| business | 运营任务 | 经营动作台账/路线图/渠道 |
| hr | ATS 节点/绩效 | 招聘运营/编制/组织变更 |
| risk | 策略草稿/案件工单 | 限额台账/模型监控 |

### 2.6 多 Agent 拓扑（对照 Ch10，服务全故事）

| 角色 | 上下文策略 | 职责 |
|------|------------|------|
| Orchestrator | 索引型（Manager） | 阶段、Skill 选择、平面调度、HITL、停止 |
| Intent+Schedule | 短槽位对话 | 会前；绑定 Org×Scenario |
| Understanding | 隔离长转写 | 质量、术语；**可触发 Knowledge 检索**辅助消歧 |
| Artifact | 按 Skill schema | 场景化多产物；引用 citation |
| Evaluator（**必做**） | **新鲜上下文**（不得复用 Generator 全文轨迹当自评） | 对照 **Skill 成功标准 + schema**；若 `mode=sop` 再对照 SOP done-criteria/checklist；不通过不得 embed |
| Knowledge Retriever | 工具化检索 | Docs + Continuum |
| WorkEmbed | 已确认产物 | 写回；嵌入前查重 |
| **Render** | 无事实发明权；**输入必须是 acl_view** | Artifact 过滤视图→邮件/HTML/图表 |
| Delivery | 投递已渲染包 | 通知≠嵌入成功；不再做事实改写 |
| Disambiguator | 跨域 | Cards + Continuum 消歧 |

**Evaluator 实现要求：** Pipeline 中独立验收阶段必须存在。可用「确定性 Hook + schema」作为核心引擎，但**不得取消该阶段**。  
- `mode=sop`：验收含 SOP checklist / done-criteria  
- `mode=playbook`：验收含 Skill 成功标准 + schema；**不要求**不存在的 SOP checklist  
高风险故事（发布/策略/合规/H5）必须再叠加独立 LLM Evaluator（新鲜上下文），禁止「生成完直接当通过」。

长产物落盘，Orchestrator 只存引用——来自 book-translation / Manager 实验的教训。

### 2.7 WorkObjectRef（统一工作对象，Phase 0 必定字段）

```text
WorkObjectRef
  ├── work_object_id         # 纪要君内部 ID
  ├── connector_id           # 哪个 Connector
  ├── org_domain             # eng|business|hr|risk|compliance
  ├── object_type            # defect|task|change|policy_draft|remediation|hc_action|...
  ├── external_id            # 外部系统主键（可空=尚未创建）
  ├── external_url           # 可选深链
  ├── status                 # draft|pending_confirm|submitted|open|done|cancelled|failed
  ├── production_effect      # none|draft_only|observe|production  （默认 none/draft_only）
  ├── idempotency_key        # 防重复建
  ├── meeting_id / artifact_id / source_spans[]
  ├── series_id / project_id # 可选，供 Continuum 关联
  ├── owner_user_id
  ├── last_synced_at / sync_error?
  └── acl_snapshot           # 写回时权限快照（审计）
```

`work_link` 表 = MeetingWorkUnit ↔ WorkObjectRef 的持久化；回流更新的是 `status` / `last_synced_at`，不是另起一套模型。

### 2.8 场景成熟度（L0–L3）与 Default Playbook 契约

`orchestration_mode` 回答「有没有场景 SOP」；**成熟度**回答「允许嵌多深」：

| 级别 | 含义 | 典型 | 允许的嵌入深度 |
|------|------|------|----------------|
| **L0** | `general` 降级 / 未知场景 | 绑不上具体 Skill | 只读写视图 + 待确认草稿；`embed_gate=block`；**本场 Pipeline 不执行 embed**。若要写入任务系统：须 **改绑到 L1+ 具体场景**（或人工升 maturity）后再跑，不得在 L0 上「确认后偷偷 embed」 |
| **L1** | playbook，产物为主 | 轻量同步、口径讨论 | 确认后可嵌**非生产**任务/台账草稿 |
| **L2** | playbook 或 sop，确认后深嵌 | R1 需求同步、B4 经营动作、**H5（playbook+critical+sealed）** | `confirm_only` 后写执行/管理对象；**仍禁** production_effect |
| **L3** | **必须 `mode=sop`** | R4 发布、K1 策略、C2 整改 | 允许在 SOP+HITL+Policy 下触及高风险/近生产路径 |

升级规则：要用生产生效 / 发布 Go / 合规「完成」闭环 → 必须升 L3 并具备真实 `steps.yaml`，禁止 playbook 硬闯。

#### Default Playbook（平台契约，不是散文）

```text
playbooks/default.yaml   # 唯一默认编排；场景 mode=playbook 时加载
steps:
  - understand
  - retrieve        # 可 skip_if no series/project
  - extract
  - artifact
  - schema_validate # Hook 墙
  - policy_hooks    # 生产禁令等；墙
  - evaluate
  - hitl            # L1/L2 默认开
  - embed           # 受 embed_gate；**L0 本场不执行**（要嵌入须先改绑 L1+ 场景）
  - continuum_index # 按 continuum_write_class 决策（与投递无关，失败不阻塞索引决策留痕）
  - render          # **先**物化 acl_view，**再**按视图渲染（禁止先渲全量再过滤）
  - notify          # Delivery：投递已渲染包；受 delivery_scope
budget:
  max_llm_calls / max_retrieve_hops / max_wall_clock
on_fail: 见 §2.11
```

场景可 **收紧** Default Playbook（多 HITL、禁 notify），不得擅自删掉 `schema_validate` / `policy_hooks` / `evaluate`。

### 2.9 工作闭环回流（一等公民，不只 create）

```text
WorkObjectRef.status 变化（Webhook / 轮询）
  → domain_event work_link.synced
  → 更新 Continuum open_work_links（关闭则移出 open）
  → 若 series 下仍有 open 阻塞：下次会前 briefing 默认置顶
  → 过期未关闭：可触发提醒事件（非自动改外部状态）
```

成功标准：**管理会看台账是否变**；架构上 `open_work_links` 会前召回与回流更新同级重要，不能只做「建单成功」。

### 2.10 跨域消歧裁决协议

```text
ambiguity_record
  ├── term / candidate_senses[] / evidence_citations[]
  ├── status: open | resolved | escalated | expired
  ├── resolved_sense / resolver_user_id
  ├── deadline
  └── effect_on_embed_gate   # 未解决时的闸门收紧
```

裁决规则：

1. 未 `resolved`：跨域产物拆分视图；**禁止**合并写成「各方已同意」；`embed_gate` 至少 `confirm_only`。  
2. 涉及 `production_effect`：未消歧 → `block`。  
3. `deadline` 默认：本场 Pipeline 结束前；超时 → `escalated` 给会议 owner / 域负责人（配置在 OrgDomain.cross_domain_policy）。  
4. 多域冲突优先级：以 **被写回系统所属域** 的释义为准做该侧产物；另一侧保留歧义标记，不覆盖。  
5. 无人裁决：整场可完成「可读产物」，但自动嵌入保持 block/confirm_only。

### 2.11 PipelineRun 预算与失败语义

```text
PipelineRun
  ├── budget: llm_calls, retrieve_hops, wall_clock, embed_attempts
  ├── failure_policy per stage
  └── terminal: succeeded | degraded_minutes_only | awaiting_hitl | failed | cancelled
```

| 失败类 | 默认语义 |
|--------|----------|
| ASR/转写质量过低 | `degraded_minutes_only` 或 `awaiting_hitl`；**不**自动 embed |
| Continuum/Docs 召回空 | 继续但 Artifact 必须标「无历史依据」；管理会系列会 → 建议 HITL |
| Evaluator 不通过 | 回退修订或 HITL；超过 N 次 → `awaiting_hitl`，不得 embed |
| Connector 超时/5xx | 幂等重试有限次 → `failed` 可补偿；禁止换参数静默再造单 |
| Policy 拒绝 | 立即停止该副作用；记录 audit；可降级只出视图 |
| 预算耗尽 | 停止 Agentic 多跳与继续生成；保留已落盘 checkpoint |

Orchestrator 必须能向对话平面解释 terminal 状态（用户可续跑 / 确认 / 取消）。

### 2.12 Presentation / Render 平面（精美纪要 ≠ 工作本身）

用户要的「漂亮纪要」——**多形态可读视图**——是一等公民交付能力，但必须挂在结构化 Artifact 之上，禁止每个渠道各自再总结一遍。

```text
Confirmed Artifacts（真相源）
  → 按收件人集合物化 acl_view[]（Policy/ACL；critical 可得到空视图=不渲染）
  → 对每个 acl_view：
       RenderEngine（确定性模板 + 图表数据绑定）
         ├── text_plain / markdown
         ├── email_html
         ├── html_report
         ├── chart_bundle   # 只绑该视图内可见数值
         └── attach_pack    # 可选；PDF V1 可后置
  → DeliveryAgent 投递对应渲染包（不再二次改写事实）
```

| 规则 | 说明 |
|------|------|
| **单一真相** | 只从已确认 Artifact 渲染；禁止「为了好看再让 LLM 重写一版事实」 |
| **先 ACL 后渲染** | **禁止**对未过滤全量 Artifact 生成可转发 HTML/图表再在投递时删减；Render 输入必须是 `acl_view` |
| **图表数据绑定** | 图表只绑定该 `acl_view` 内数值/序列；缺数显示「数据不足」，**禁止臆造** |
| **模板按场景** | Skill Pack 可挂 `render/`；无则用平台 Default Render Pack |
| **critical 默认** | `delivery_scope` 导致无收件人或策略禁分发时：**跳过 Render**（不落可转发长文），仅审计留痕 |
| **与嵌入解耦** | 邮件再漂亮也不算 WorkEmbed 成功；管理会成功仍看台账/看板 |
| **可再渲染** | Artifact 不变时换模板 = 对已有 `acl_view` 轻量重跑 Render（不重跑 Understanding） |

Skill Pack 增量：

```text
skills/<org>/<story_id>/
  render/
    email_html.j2
    charts.yaml
    html_report.j2
```

平台默认：`render/default/`（通用纪要邮件 + 行动项表 + 可选简单图）。  
Delivery 渠道：企微、邮件（MIME plain+html）、内网 HTML 链接。  
`task_delivery_log`：channel、template_id、recipient_set、render_hash、**acl_view_id**。


### 2.13 Artifact 公共信封（所有场景 schema 之上）

场景 `required_artifacts[]` 可以不同，但**每条 Artifact 必须套公共信封**，否则 Evaluator / Render / Continuum 无法统一处理：

```text
ArtifactEnvelope
  ├── artifact_id
  ├── meeting_id / org_domains[] / scenario_type / skill_pack_id
  ├── artifact_kind          # decision|action_items|risks|verdict|metrics|draft|...
  ├── schema_id / schema_version
  ├── payload                # 场景字段（唯一可变体）
  ├── confidence             # 0..1 或 low|med|high
  ├── unresolved[]           # 未决项（禁止静默当成已决议）
  ├── source_spans[]         # 转写/材料定位
  ├── references[]           # Docs/Continuum citation
  ├── chart_series[]?        # { series_id, label, points[{x,y}], unit } 仅事实数据
  ├── classification         # 继承或收紧本场密级
  ├── continuum_write_class  # 本产物写入策略（可严于场景默认）
  └── created_by_stage       # understand|artifact|hitl_patch|...
```

铁律：Render 的图表**只读 `chart_series` / payload 内已声明数值字段**；Envelope 缺数 → 显示数据不足，禁止补造。

### 2.14 Domain Event 目录（双平面咬合契约）

事件是 Dialog / Pipeline / Render / Connector 回流的唯一握手语言。V1 **必须**支持下列事件（名称为权威）：

| 事件 | 生产者 | 消费者 | 用途 |
|------|--------|--------|------|
| `meeting.scheduled` | Schedule | Knowledge briefing | 会前检索触发 |
| `transcript.ready` | 转写接入 | Pipeline | 启动会后流水线 |
| `understanding.completed` | Understanding | Orchestrator | 含低可懂/未知术语摘要 |
| `ambiguity.opened` / `ambiguity.resolved` | Disambiguator | Policy/Embed | 闸门收紧/放松 |
| `artifact.persisted` | Artifact | Evaluator/HITL | 待验收 |
| `evaluation.failed` / `evaluation.passed` | Evaluator | Orchestrator | 不得/允许 embed |
| `hitl.requested` / `hitl.resolved` | Orchestrator | Dialog | 人工确认 |
| `work_link.submitted` | WorkEmbed | 审计 | 已向外部提交 |
| `work_link.synced` | Connector webhook/轮询 | Continuum/Dialog | 状态回流；更新 open 项 |
| `continuum.write_decided` | Knowledge | 审计/Eval | 含 write_class 与拒写原因 |
| `render.completed` / `render.skipped` | Render | Delivery | skipped=无 acl_view/禁分发 |
| `delivery.sent` / `delivery.suppressed` | Delivery | 审计 | suppressed=critical 策略 |
| `pipeline.terminal` | Pipeline | Dialog | succeeded/degraded/awaiting_hitl/failed… |
| `budget.exhausted` | Pipeline/Knowledge | Orchestrator | 停止多跳/继续生成 |

规则：跨平面通信优先事件，不靠轮询共享可变大对象；大对象只传 ID。

### 2.19 向量存储决策原则（选型可晚，原则要早）

## 3. 主链路如何托住「执行会 + 管理会」

### 3.1 会前（Dialog）— 默认带 Knowledge

```text
用户 NL
 → Intent（场景粗分 + 条线提示 + series/project 线索）
 → 加载 Skill index
 → Schedule 生成 MeetingDraft（purpose/success_criteria/org_domains/series_id?）
 → Policy 定密级与 knowledge_scopes
 → HITL（高风险预订）
 → 【默认】Knowledge briefing（不是可选彩蛋）：
      - Continuum：同系列/项目历史会的 open_artifacts / open_work_links
      - Docs：本场相关行内文档 Top-K（带 citation）
 → 把 briefing 摘要放进状态栏/草稿，供会上对照
```

**绿场实现（jiyaojun，2026-08-06 第五轮收口）**  
- **Session journal**：branch marker **自身为 active leaf**；fork 后 append 新分支；跨 JSONL repo resume 排除旧分叉；forward parent illegal；50 并发 append 不丢（**JSONL 仅同进程**）。  
- **HITL**：suspend 存当时 discovery grant；resume = allowlist ∩ grant；中文建任务/建缺陷选对 connector。  
- **对象授权**：session_meta owner/org 不可变；BFF 传 principal；跨用户 chat/resume/context/task 全拒。  
- **BoundedAgentLoop**：**Mock planner**；tool→observation→再决策；与会后 `StepEngine` **分离**。  
- **调度**：in-process + **合作式 cancel**；journal 任务投影；重启未终态 → orphan/needs_resume。

### 3.2 会后流水线（Pipeline）— 理解与产物都可检索

```text
转写就绪事件
 → AuthZ
 → Understanding（词表 + 必要时 RAG）
 → 读取 Skill.orchestration_mode
 → 【mode=sop】`Orchestrator` → `sop_executor`：按 `sop/steps.yaml` 逐步推进（`StepEngine` 阶段式状态机，非 ReAct）
 → 【mode=playbook】`playbook_executor`：平台 Default Playbook + 场景 `playbook_overrides.yaml`
 → 【未知/L0】`platform/general` 安全降级（`pipeline_path=fallback`；跳过 embed / Continuum wide）
      仍执行 Policy / 生产禁令 / schema Hooks（墙不因无 SOP 而消失）
 → Artifact（对照 Docs/Continuum + schema；mode=sop 时再对照 SOP checklist；references[]）
 → **必做 Evaluator**（不通过则回退/HITL，不得 embed）
 → HITL（playbook 默认更严）
 → WorkEmbed
 → Continuum 索引写回（按 continuum_write_class；与投递无关）
 → **按收件人物化 acl_view → Render**（无视图则跳过，不落可转发长文）
 → Delivery（投递已渲染包；critical 默认 off 或极窄）
 → 回流事件
```

### 3.3 管理会与执行会的架构差别（同一套骨架，不同 Skill/Connector）

| | 执行会 | 管理会 |
|--|--------|--------|
| 成功标准 | 单/工单/变更草稿落地 | 看板/台账/版本/限额结论落地 |
| 典型危险 | 建错单 | 写错状态、误触发生产生效、敏感扩散 |
| Skill 重点 | artifact→执行 Connector | artifact→管理 Connector；常会前拉台账 |
| 评测重点 | 字段映射、幂等 | 状态机合法、权限、禁止生产热切换 |

### 3.4 极高敏故事的架构特判（H5 等）

Policy 模板 `classification=critical`：

- Pipeline 默认 `embed_gate=confirm_only` 或分步确认  
- Delivery 默认 off  
- 检索与日志强脱敏  
- 禁止 discover 到「通知当事人」类工具  
- **`continuum_write_class=sealed`（或 `none`）**——禁止写入宽 Continuum  
- Eval 必须含：泄露/误通知/误入宽检索 负例  

这不是产品例外，是 **Ch10-8 信息权限** 在银行场景的落地。

## 7.5 业界最新方案对齐（2025–2026，与本书互补）

> 李博杰书提供 Agent 原理与实验；下列为同期产业共识，用来校准「SOP / Skills / Harness」落地形态。不替代书，只补齐工程口径。

| 趋势 | 要点 | 纪要君落点 |
|------|------|------------|
| **Harness Engineering** | 模型不是产品；确定性运行时校验/授权/执行/记账；LLM 不直连工具 | 已有 ToolRuntime；**Hooks=墙**（SOP validate/生产禁令） |
| **Agent Skills 开源标准** | 程序性知识打包；三级渐进披露；Skills 教流程，MCP/工具负责连接 | Skill Pack + `sop/` + Knowledge `references`；Connector≈工具面 |
| **MCP** | 工具与数据连接标准化 | **Connectors 必须支持 MCP 暴露/接入**（可另有原生适配，但不能只有无协议私接） |
| **SOP→结构化计划** | 模糊 SOP 先澄清再 Planner 成步骤图再执行 | **有行内 SOP 的场景**入库并编译为 `steps.yaml`；**无 SOP 不强制编造**；走 Default Playbook；歧义进 HITL |
| **Planner / Generator / Evaluator 分离** | 自评有偏，评估用新鲜上下文 | Pipeline **必须**含 Evaluator 阶段；与 Artifact 分离 |
| **Sprint / Done Contract** | 先定义完成再干活 | 故事成功标准 + schema = done contract（**必填**）；有 SOP 时再叠加 checklist |
| **Context reset vs 无限压缩** | 长任务分阶段换干净上下文 | 双平面 + Ch10 阶段换角色；大产物落盘只留索引 |
| **Budget / 停止条件** | 长任务要有预算与终止 | PipelineRun 预算；Map-Reduce 轮次上限 |
| **可观测与评测门禁** | 无轨迹无治理 | domain events + 故事评测族 + harness 安全评测（注入/越权） |

参考入口（便于后人追溯，非广告）：

- Anthropic Engineering: Agent Skills / progressive disclosure；长程 Agent 的 harness 讨论  
- Agent Skills open standard（跨平台可移植程序性知识）  
- Tomasz Tunguz 等对 harness 七要素（retrieval、tools、loop、state、sandbox、obs、cost）的归纳  
- 产业侧 SOP 多智能体：Clarifier→Planner→Implementor；Agent-Ops 类 SOP 编排  
- LangGraph 等：有状态图、HITL、检查点（与现有技术选型可兼容，但契约以本文为准）

**取舍：** 不把纪要君做成「通用 SOP RPA 平台」；只做**会议工作单元上的场景 SOP**——SOP 的触发是会议目的与转写/台账，不是任意桌面操作。
