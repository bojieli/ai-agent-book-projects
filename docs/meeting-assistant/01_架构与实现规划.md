## 0. 结论先讲

纪要君不应继续在现有 preview 上「修修补补」。现有实现的主要问题不是缺某个小功能，而是：

1. **双栈分裂**（LangGraph 预订层 vs Flask 纪要层）导致没有单一真相源  
2. **中间件动物园**把可靠性当成事后补丁，而不是一等公民的 Harness  
3. **入口与版本爆炸**（`meet_agent_*` / HITL / enforcer 多版本并存）  
4. **产品边界残缺**：会后是占位，代办闭环基本停在设想  
5. **领域模型过窄**：把会议当成「预订对象 + 纪要文本」，而不是**有目的的工作单元**  
6. **默认假设「通用模型听得懂」**：行内系统名、流程黑话、项目代号，ASR/通用 LLM 经常听不懂、听错、装懂  
7. **工作嵌入过浅**：停在「发纪要 / 发代办消息」，没有按金融场景把结果写回真实工作系统

**场景边界：只服务微众银行这类金融企业内部会议，不做消费级对外会议产品。**

**正确抽象：**

```text
内部会议 = 某组织条线（研发 / 业务 / HR / 风控安全…）上的一次受控协作
产物 = 该条线 × 该场景约定的工作结果（不止纪要）
价值 = 结果进入该条线真实工作系统，并按权限回流
黑话 = 按组织域隔离的可懂性资产，禁止「全行一本词表硬套」
```

纪要是**默认可读视图**，不是终点——但视图本身要够用：可渲染为精排版邮件、图表、HTML 报告。系统从第一天按这条链设计：

```text
组织条线（Org Domain）× 场景类型（Scenario Profile）
  → 目的与成功标准
  → 分域领域上下文（该条线词表/实体/材料，ACL 过滤）
  → 会前准备 / 可控预订
  → 会中留痕（显式「听不清 / 术语未知 / 跨域歧义」）
  → 场景化多产物（研发单 / 业务跟进 / HR 流程项 / 风险变更…）
  → Work Embedding（写入对应工作系统，可追踪回写）
  → 权限、合规、审计全程约束
```

技术骨架（v7，细节见 03）：

```text
Scenario Skill Packs（**SOP 按需**：有行内流程才挂 `steps.yaml`，否则 Default Playbook）
  ×  Org Domain + PolicyEngine + **Hooks 墙**（模型不可跳过校验/生产禁令；与有无 SOP 无关）
  ×  Dialog Plane + Pipeline Plane（按 SOP 或 Playbook 编排长任务，不堵对话）
  ×  Orchestrator Manager + **必做 Evaluator**（新鲜上下文验收，禁止生成者自评）
  ×  Domain Cards + **Meeting Knowledge Plane**（行内文档 + 跨会 Continuum；SOP 原文有则入库）
  ×  ToolRuntime Harness（LLM 不直连工具；**Connector 必须可走 MCP**）
  ×  评测按故事 ID（含步骤合规负例——仅对 `mode=sop`；越权负例全覆盖）
```

可复用：领域适配经验、Map-Reduce、HITL、幂等思路。  
废弃：双脑、中间件堆、`会议=写纪要`、`闭环=发个企微代办`、听不懂还装懂、全量工具塞上下文、事后补功能。

> **自 v7 起：第 3–4 章「原则与目标架构」的权威叙述以 [03](./03_架构v7_对照李博杰实验与全场景.md) 为准；下文保留条线/产品契约，架构图若与 03 冲突以 03 为准。**

## 1. 产品定义（一次定死）

### 1.1 一句话

**纪要君是面向微众银行等金融科技内部的会议工作嵌入 Agent：按「组织条线 × 会议场景」产出不同工作结果，用该条线的黑话与知识去理解会议，并在权限与确认约束下写回对应工作系统；纪要只是默认可读视图。**

### 1.1.1 场景边界：金融内部，按条线嵌入工作

| 做 | 不做 |
|----|------|
| 行内会议（组织账号、通讯录、日历、企微、各部门工作系统） | 对外公开 webinar / 消费级会议 SaaS |
| 覆盖**研发科技 / 业务 / HR / 风控 / 合规**，并支持跨条线会 | 假装全行只有一种会议、一本黑话 |
| 按条线×场景产出**可执行工作结果**并写回系统 | 只生成漂亮纪要发给群里就结束 |
| 分域术语（研发 ≠ 业务 ≠ HR ≠ 风控 ≠ 合规） | 全行共用一张词表硬套所有会 |
| 按部门/项目/密级/场景控权 | 「同公司登录即可看全部会议内容」 |
| 听不懂/跨域歧义就标注、澄清后再落地 | 听不懂却自动写成决议并触发变更 |

在微众这类金融科技公司，会议价值在于：**有没有把该条线的工作往前推一步**——研发推进需求/缺陷/发布，业务推进活动与口径，HR 推进流程节点，风控推进策略与处置，合规推进口径与整改——而不是多一篇人人都可能看不懂的摘要。

详细故事见：[02_场景故事集.md](./02_场景故事集.md)。

### 1.2 先分组织条线，再分会议场景

同一套「转写→总结」对所有部门都不够。必须同时有两层配置：

1. **Org Domain（组织域 / 条线）**：这拨人日常用什么黑话、默认连哪些工作系统、密级基线是什么  
2. **Scenario Profile（场景档案）**：这场会要产什么结果、写回哪里、谁确认  

#### 1.2.1 组织条线（金融科技，含风控与合规）

| 组织条线 | 他们开会通常在解决什么 | 真正有用的结果 | 典型工作嵌入 | 黑话特征 | 密级基线 |
|----------|-------------------------|----------------|--------------|----------|----------|
| **研发 / 科技** `eng` | **执行**：需求/方案/缺陷/发布；**管理**：交付、资源、治理、优先级 | 任务缺陷发布对象 + **里程碑/资源/治理/OKR 决议** | 研发协作、缺陷、变更发布、**项目交付看板、排期、治理台账** | 服务名、灰度(发布)、里程碑、人月、技术债 | 中（资源会偏高） |
| **业务** `business` | **执行**：活动/口径/客诉；**管理**：经营分析、额度定价建议、路线图、渠道 | 业务任务 + **经营动作/决策台账** | 业务项目、运营任务、**经营看板** | 客群、转化、额度、漏斗 | 中（额度相关偏高） |
| **HR** `hr` | **事务**：招聘/校准/政策；**分析**：漏斗、编制、**组织调整/减员方案** | 流程节点 + **招聘运营/组织变更分析** | ATS、绩效、**编制/组织变更台账** | HC、漏斗、人效、方案版本 | **高 / 极高（H5）** |
| **风控** `risk` | **执行**：策略/误杀/案件；**管理**：限额组合、模型表现、欺诈专项 | 变更草稿/工单 + **风险看板与监控台账** | 策略流、处置系统、**限额/模型监控** | 策略 ID、误杀、限额、PSI | **高** |
| **合规** `compliance` | **事项**：口径/整改/评估；**管理**：制度、迎检、合作方 | 台账结论 + **制度/迎检/合作方管理对象** | 合规台账、整改、**制度库/迎检台** | 口径、证据、检查要点 | **高** |
| **跨条线**（非独立枚举；`org_domains[]` 多选） | 科技↔业务、业务↔风控、科技↔合规等 | 消歧记录 + 分条线写回 | 多 Connector | 同词异义高发（如「灰度」） | 取参与域最高密级 |

> **安全运营类会议 V1 挂 `risk` 域**（不单列 `security` 枚举）；故事集处置/复盘叙事仍适用。系统名以行内为准，架构只要求 Connector 可插拔。

#### 1.2.2 同一类会，落在不同条线结果完全不同

| 会议形态 | 研发 | 业务 | HR | 风控 | 合规 |
|----------|------|------|-----|------|------|
| 同步/排期 | sprint 任务与技术阻塞 | 业务里程碑与依赖 | 招聘漏斗/HC（高敏） | 策略观察窗口与样本积压 | 整改项到期与材料缺口 |
| 评审 | 技术方案 verdict → CR | 活动/方案结论 → 业务审批 | 政策方案 → HR 流程 | 策略能否 Shadow/灰度 | 新业务可做/有条件可做 |
| 复盘 | 故障根因与改项 | 活动归因与下轮动作 | 周期改进（克制分发） | 误杀/案件归因与动作 | 检查问题归因与整改 |
| 决策 | 选型/是否发布 | 是否推全、额度调整 | 编制/政策生效（强 HITL） | 是否对生产策略生效（强 HITL） | 对外口径版本生效（强 HITL） |
| 敏感 | 少自动产物 | 少自动产物 | **默认不群发、不宽检索** | 案情/策略细节受控 | 监管材料受控 |

完整故事见 [02_场景故事集.md](./02_场景故事集.md)：  
研发执行 R1–R4 + 管理 R5–R8；业务执行 B1–B3 + 管理 B4–B7；HR 事务 H1–H3 + 分析 H4–H6（含极高敏减员分析）；风控执行 K1–K3 + 管理 K4–K6；合规事项 C1–C3 + 管理 C4–C6；以及跨条线 X1–X4。

#### 1.2.3 组织域 + 场景档案最小字段（V1 契约）

```text
OrgDomain
  ├── org_domain_id          # eng | business | hr | risk | compliance
  │                          # （安全运营会 V1 挂 risk；独立 security 域待正式注册）
  ├── display_name
  ├── glossary_scopes[]
  ├── default_connectors[]
  ├── default_classification
  └── cross_domain_policy    # 消歧超时升级给谁、多域冲突怎么拆产物

ScenarioProfile
  ├── scenario_type
  ├── org_domains[]
  ├── purpose_template
  ├── required_artifacts[]
  ├── work_bindings[]        # { org_domain, connector, object_type, hitl_roles[]? }
  │                          # hitl_roles 只能加严确认人，不得另设第二套闸门；运行时仍只认 embed_gate
  ├── glossary_scopes[]
  ├── acl_profile
  ├── classification         # public|internal|confidential|critical（旧称 sensitivity；critical=极高敏）
  ├── orchestration_mode     # sop | playbook
  ├── maturity_level         # L0|L1|L2|L3（嵌多深；L3 必须 sop）
  ├── default_embed_gate     # allow | confirm_only | block（唯一场景默认；废止 auto_embed_policy）
  ├── continuum_write_class  # wide | domain | sealed | none
  └── retention_class
```

**铁律：**

1. 没有 `OrgDomain` + `ScenarioProfile`，不允许自动 Work Embedding。  
2. 未知组合降级 `general`：固定 playbook + **L0**；只产可读纪要 + 待确认草稿，不写高风险系统。  
3. **词表按域加载**：跨条线会显式消歧（裁决协议见 03 §2.10）。  
4. **不是每个场景都有 SOP**：有行内流程才 `orchestration_mode=sop`；**禁止空壳 SOP**。  
5. **嵌入闸门单一真相**：场景 `default_embed_gate` + Policy 运行时取更严；旧名 `auto_embed_policy` 仅作别名映射。

### 1.3 会议的本质：工作单元，不是文档任务

```text
MeetingWorkUnit
  ├── org_domains[]        # 本场涉及条线（多选=跨条线；无单独 cross 枚举）
  ├── scenario_profile_id / skill_pack_id
  ├── purpose / success_criteria
  ├── stakeholders / domain_scope
  ├── glossary_scopes[]
  ├── policy_binding_id / pipeline_run_id
  ├── classification / continuum_write_class / embed_gate（运行时快照）
  ├── artifacts[] / work_links[]
  ├── ambiguity_records[]
  └── understanding
```

### 1.4 工作嵌入（Work Embedding）：按条线进入不同工作

```text
浅嵌入（不够）：会议 → 纪要 Markdown → 企微群通知
中嵌入（底线）：会议 → 结构化行动项 → 通用任务系统 + 状态回写
深嵌入（目标）：
  研发会 → 缺陷/需求/发布对象
  业务会 → 业务任务/审批节点
  风控会 → 策略变更草稿/观察任务/处置工单（确认前不对生产生效）
  合规会 → 口径版本/整改台账/评估结论
  HR 会  → HR 流程节点（强权限、少分发）
  跨条线 → 先消歧，再分别写回各方系统
```

深嵌入要求从第一天具备：

1. **统一工作对象模型** `WorkObjectRef`（字段以 03 §2.7 为准）  
2. **Connector SPI**（按条线挂载，全部走 ToolRuntime；MCP 可接入）  
3. **确认策略 = `default_embed_gate` + 运行时取更严**  
4. **双向回链 + 状态回流**（会议 ↔ 工作对象；open 项会前置顶）  
5. **失败可补偿 + 幂等 + PipelineRun terminal 语义**

```text
WorkObjectRef（摘要，完整见 03）
  work_object_id, connector_id, org_domain, object_type,
  external_id, status, production_effect, idempotency_key,
  meeting_id, artifact_id, source_spans[], owner_user_id, acl_snapshot
```

### 1.5 分域黑话：各部门「听不懂」不是同一类问题

「不一定听得懂」要按条线拆开，不能只用一个 ASR 置信度糊弄：

| 层 | 现象 | 研发 | 业务 | HR | 风控 | 合规 | 正确做法 |
|----|------|------|------|-----|------|------|----------|
| 声学/转写 | 字转错 | 服务名转成常用词 | 产品/渠道名转错 | 人名/职级转错 | 策略 ID 转错 | 条款名转错 | 低置信 span，可回听 |
| 条线术语 | 字对了但不懂 | 泳道、容量水位 | 转化、客群口径 | HC、band | Shadow、误杀、名单 | 报送口径、留痕 | 只加载本场词表桶 |
| 跨域同词异义 | 都「认识」但意思不同 | 灰度=发布 | 灰度=客群放量 | 少用 | 灰度=策略放量 | 少用或另义 | 强制消歧确认 |
| 业务意图 | 定没定不清楚 | 「先观察再发」 | 「先小流量看看」 | 「先对齐口径」 | 「先 Shadow」 | 「先内部口径」 | 未决标 unresolved，禁止自动嵌入 |

**产品铁律：**

- 听不懂 ≠ 可省略  
- 用错条线词表 = 另一种「装懂」，比听不清更危险  
- 跨条线会默认运行时 `embed_gate` 至少 `confirm_only`，直到消歧完成  

V1 **Enterprise Domain Layer** 必须支持分域：

```text
OrgDomain
  └── Domain Glossary（按 eng/business/hr/risk… 分桶）
        + 别名 / 同音 / 禁用于外域投递标记
Entity Registry（人/系统/项目/产品/流程，带 org_domain + ACL）
Meeting-scoped Retrieval（只检索本场 scopes 内材料）
Unknown Term Queue（回写时必须指定 org_domain，避免污染别的条线词表）
CrossDomain Disambiguation（跨条线会专用）
```

### 1.6 完整能力边界

#### V1 必须具备（实现可分阶段，契约必须一次出现）

| 域 | 必须能力 | 非目标（不进 V1 主路径） |
|----|----------|-------------------------|
| 条线与场景 | OrgDomain + ScenarioProfile；创建会时可指定/推断条线 | 假装全行一种会 |
| 会前 | 目的/议程/成功标准/领域锚点；预订 CRUD + HITL | 通用闲聊、对外 SaaS |
| 分域可懂性 | 分条线词表；跨域消歧；未知术语按域回写；低可懂不自动确认 | 「一张全行词表打天下」 |
| 场景化产物 | 按 条线×场景 生成 artifacts；低置信强制确认 | 实时同传、会中语音打断 |
| **可读渲染** | Artifact→markdown/邮件 HTML/图表/HTML 报告；模板可换、事实不换 | 每个渠道各写一篇互不一致的「漂亮稿」 |
| 工作嵌入 | Connector SPI + ≥1 真实 Connector；写回前确认；HR 更严默认 | 只发群消息假装闭环；一次接完所有部门系统 |
| 权限 | ACL、密级、最小必要投递/写回；HR/敏感会默认高敏 | 「登录即可看全部会」 |
| 扩展骨架 | Org/Scenario/Artifact/Connector/Glossary 注册表 | 无契约堆 Agent 文件 |
| 治理 | 幂等、checkpoint、幻觉治理、评测、成本分层 | 纯 Prompt Demo |

#### 架构预留、可插拔扩展（契约现在就要能接）

| 扩展 | 依赖契约 |
|------|----------|
| 研发缺陷/需求/发布 Connector | WorkObjectRef + eng OrgDomain |
| 业务任务/审批 Connector | business OrgDomain |
| HR 流程 Connector（强 ACL） | hr OrgDomain + 高敏策略 |
| 安全/风控/合规 Connector | risk/compliance 域（安全运营挂 risk） |
| 跨条线双语纪要视图 | cross_domain_ambiguity + 分视图渲染 |
| 部门词表运营后台 | glossary 分桶 + 审批回写 |
| 会中实时辅助 | RealtimeSession 预留（不进 V1） |

> **「不要后面补充功能」**：不是 V1 覆盖所有部门所有系统，而是 **组织域、场景、分域黑话、产物、工作对象、Connector、权限** 契约一次正确。以后每接入一个部门，是加 OrgDomain 配置 + 词表桶 + Connector，不是翻修内核。

### 1.7 成功标准（工程可测）

| 指标 | 目标口径 |
|------|----------|
| 条线×场景覆盖 | 能绑定 OrgDomain + Scenario；未知安全降级 |
| 分域词表正确性 | 研发会不误用 HR 词表释义；跨域歧义必须露出 |
| 高风险可控 | 预订写回与工作写回均按策略确认；HR 默认更严 |
| 工作嵌入真实性 | 至少一条主路径（建议先研发或通用任务）产物→外部对象→回流 |
| 浅闭环不算完成 | 仅群发纪要不算场景成功（除非显式配置） |
| 低置信/未知术语 | 不得静默确认决策或自动建单 |
| 权限正确性 | 无授权读转写/产物/他域词表/工作回链：0 容忍 |
| 成本 | 只注入本场 glossary_scopes，禁止全量词表进 Context |

## 2. 现状诊断：为什么不能「渐进修补」

### 2.1 当前真实结构

```text
jiyaojun-preview/
├── LangGraph 预订层（agents/middleware/sdk/...）
│   └── PostMeetingAgent = 占位
└── 嵌套 jiyaojun/ Flask 生产纪要
    └── smart_summary Map-Reduce + auto_task 发送
```

简历与面试文档里的「Orchestrator + TodoAgent + SSE + Redis」是**目标叙事**，不是当前代码真相。

### 2.2 核心病灶

| 病灶 | 表现 | 为什么致命 |
|------|------|------------|
| 双脑 | 预订与纪要两套运行时 | 状态、权限、审计、幂等无法统一 |
| 中间件堆叠 | enforcer/hallucination/validator 多版本并存 | 可靠性逻辑分散、难测、难推理 |
| 入口爆炸 | 多个 `meet_agent_*`、HITL client 变体 | 「生产入口是谁」不可回答 |
| 文档噪音 | 大量 fix report | 掩盖架构真相，新人无法建立模型 |
| 补丁式演进 | 先能跑再补 HITL/幻觉/幂等 | 数据模型与控制流被历史债务锁定 |
| 企业耦合裸奔 | SSL verify 关闭、环境硬编码痕迹 | 安全与可移植性同时受损 |

### 2.3 决策

**以新代码树重建（Greenfield），旧代码只作参考实现与回归样本来源。**  
不是 fork 修修补补，而是：

- 抽取可验证的领域行为（预订参数、纪要结构、工具契约）  
- 用评测集固化这些行为  
- 在新架构里重新实现并通过评测

## 4. 目标架构

> **权威总图、双平面、Skill Pack、PolicyEngine、Connector 发现、代码树 → [03 §2–§6](./03_架构v7_对照李博杰实验与全场景.md)。**  
> 下面保留与产品契约相关的摘要，避免与 03 双源冲突时各改各的。

### 4.1 架构摘要（v7）

```text
Channel/AuthZ
  → Orchestrator（Manager：Org×Scenario Skill，阶段控制）
       ├ Dialog Plane（预订/HITL/插话）
       ├ Pipeline Plane（理解→产物→嵌入→回流）
       ├ Presentation/Render（**先 acl_view 再**邮件/图表/HTML → Delivery）
       └ PolicyEngine（密级/embed_gate/生产生效/分发/写库类）
  → ToolRuntime（唯一副作用）
       ├ Meeting/IM APIs
       ├ Domain Layer（分域词表/RAG/消歧）
       └ Work Connectors（执行系 + 管理系，可发现）
  → Eval（按 02 故事 ID）
```

### 4.2 铁律（升级版）

1. Agent 禁止直连外部 HTTP；副作用只经 ToolRuntime。  
2. 无 OrgDomain×Scenario Skill，禁止自动 Work Embedding。  
3. 理解不足或消歧未完成，禁止生产生效类写回。  
4. 业务额度建议、风控策略、HR 组织调整：默认不能「会上说说」就生效或群发。  
5. 管理会成功标准看台账/看板，不看是否发出纪要或邮件是否漂亮。  
6. **每个上线场景必须有 Skill Pack**（含 mode、maturity、default_embed_gate、eval）；**仅 mode=sop / L3 才要求 steps.yaml**；无 SOP 走 Default Playbook，禁止空壳。  
7. **Pipeline 必须含 Evaluator**；不通过不得 WorkEmbed。  
8. **Connectors 必须可经 MCP 接入**；Knowledge briefing + **按 continuum_write_class 的写回决策**为必做。  
9. **嵌入闸门只有 `embed_gate` 一条链**（场景默认 + 运行时取更严）。  
10. **Render 必须先物化 `acl_view` 再渲染**；禁止先渲全量再过滤；图表禁止臆造数值；平台须有 Default Render Pack。  
11. 与 03 冲突时以 03 为准（含 **§4 表清单**）。

### 4.3 Agent 与状态模型

仍采用 Intent / Schedule / Understanding / Artifact / Evaluator / WorkEmbed / **Render** / Delivery / HITL；跨条线增加 Disambiguator；Knowledge Retriever 为工具化检索角色。  
状态模型在原 MeetingWorkUnit 上必含：`skill_pack_id`、`policy_binding_id`、`pipeline_run_id`、`ambiguity_records`、执行与管理两类 `work_links`。

详细字段与事件名以 03 与后续 DDL 草案为准；**不要在 01 再维护一份会过期的大图。**

## 5. 核心链路（V1 全覆盖）

### 5.1 会前：场景绑定 + 可控预订

```text
用户 NL
  → IntentAgent（intent + scenario_hint + slots + confidence）
  → 低置信度？澄清 : 继续
  → 绑定 ScenarioProfile（未知则 general 降级）
  → ScheduleAgent 生成 MeetingDraft（含 purpose/domain_scope）
  → 高风险？HITL : 只读可直出
  → ToolRuntime 执行（幂等）
  → 【默认】Knowledge briefing：行内文档 + 同系列历史会未关闭项（ACL）
  → 回复用户
```

硬规则：

1. create/update/cancel **永远** HITL  
2. `user_id` / AuthZ 从 session 注入，模型不可覆盖  
3. 成功以 ToolRuntime 记录为准  
4. 场景绑定失败只降级，不臆造高风险 work_bindings  
5. **能识别系列/项目时，跨会 Continuum 检索是默认开启，不是彩蛋**

### 5.2 会后：先理解，再按场景产多产物

```text
FetchTranscript
  → AuthZ：当前用户/任务是否有权处理该会
  → Normalize + PII/密级策略
  → UnderstandingAgent
       - 质量/低置信 span
       - 术语实体链接（Domain Layer，ACL 内）
       - unknown_terms + embed_gate
  → embed_gate=block？ → 只出待确认草稿，停止自动嵌入
  → 按 Skill.orchestration_mode：
       - sop → 按 steps.yaml + validate Hook
       - playbook → 平台 Default Playbook（无场景 SOP）
  → ArtifactAgent（按 Scenario.required_artifacts / schema）
       - Map-Reduce 分片（可并行）
       - Reduce 成多产物；**结构化字段是真相，markdown 只是默认视图之一**
  → Evaluator（schema/成功标准；mode=sop 时含 checklist）
  → Persist artifacts
  → HITL：确认关键产物（playbook / 金融默认开）
  → WorkEmbedAgent
  → Continuum 索引写回（按 write_class）
  → 物化 acl_view → **RenderEngine**（无视图则跳过）
  → DeliveryAgent（投递已渲染包）
```

算法取舍：

- Map-Reduce，不选 Refine  
- **先 Understanding，后 Artifact**——不懂就产草稿，不直接写工作系统  
- **同一份 artifacts，多形态渲染**；禁止每个渠道各总结一次  
- **先 ACL 视图，后渲染**；图表只绑视图内数值；缺数明示，禁止臆造  
- 渲染再漂亮 ≠ WorkEmbed 成功

### 5.3 深嵌入：结果进入工作，而不是停在通知

```text
confirmed artifacts
  → WorkEmbedAgent 按 work_bindings 映射 WorkObjectDraft
  → 确认策略：运行时 `embed_gate`（场景默认取更严；HITL / 责任人）
  → ToolRuntime → Work Connector.create/update
  → 写 work_links + 幂等键
  → Continuum 索引写回（可与下步并行）
  → 物化 acl_view → Render（精美邮件 / 图表 / HTML；无视图则跳过）
  → DeliveryAgent 投递已渲染包（不是又一次「自由发挥总结」）
  → 外部状态回流 → domain_event `work_link.synced`
  → 催办只针对未关闭 WorkObject / Action，不是对纪要本身催办
```

**完成定义（金融口径）：**

- **`general`/L0**：本场只出可读视图 + 待确认草稿，**不**在 L0 上 embed；要写入任务系统须改绑 L1+ 场景（如通用行动项场景）后再确认嵌入  
- L1+ / 安全/风控/变更等：至少能演示「产物 → 外部工作对象 → 回链可点 → `work_link.synced` 回流」  
- **仅群发纪要，不算该场景成功**

### 5.4 权限主路径（与业务同级）

```text
谁可以：预订 / 看转写 / 看产物 / 触发写回 / 看 work_links / 改词表
  → 默认：主持人 + 参会人最小集
  → 场景可收紧（敏感会、合规会）
  → 投递与写回前再次 AuthZ（防 HITL 后换人越权）
  → 领域检索结果按 ACL 过滤后再进 Context
```

## 6. ToolRuntime（取代中间件动物园）

### 6.1 为什么集中

现有 `tool_call_enforcer_v1/v2/v3`、多套 hallucination_*、validation_* 并存，说明问题被重复「发现」而没有被「拥有」。  
可靠性必须有唯一所有者：`ToolRuntime`。

### 6.2 执行管线（每次副作用）

```text
1. Plan        Agent 产出 ToolCallIntent
2. Authorize   风险等级 / ACL / 场景策略 / HITL 票据
3. Validate    JSON Schema + 业务校验 + WorkObject 字段校验
4. Idempotency 查 idempotency_key → 命中则返回历史结果
5. Execute     Integration / Work Connector
6. Verify      返回契约校验；无真实调用却声称成功 → 幻觉
7. Correct     可恢复重试；幻觉补执行（仍走 3~6）
8. Audit       tool_call_log + domain event（金融可追责）
```

### 6.3 幻觉定义（唯一标准）

| 情况 | 判定 |
|------|------|
| message 无 `tool_calls`，但文本声称已创建/取消/发送/建单 | **幻觉** |
| 有 `tool_calls`，工具返回 error | **执行失败**（非幻觉） |
| 有 `tool_calls`，成功且日志可核对 | **成功** |

补执行必须二次走幂等，禁止「修幻觉时重复建会/建单」。

### 6.4 幂等键设计

```text
idempotency_key =
  hash(user_id, tool_name, canonical_args, time_bucket | business_key)

示例：
- 创建会议：user_id + title + start_time + attendees_canonical
- 发送纪要：meeting_id + channel + template_version
- 创建工单/任务：meeting_id + artifact_id + connector_id + object_type
- 策略变更草稿：meeting_id + change_proposal_hash
```

存储：MySQL `tool_call_log` 为权威；Redis 可做短 TTL 加速，不作为唯一真相。

## 11. 为什么这么设计（取舍说明）

### 11.1 为什么不是「纪要工具」

在微众这类金融科技公司，会议是工作协作节点。只写纪要 = 结果停在聊天里。  
差异化在 **条线×场景产物 → 工作系统嵌入 → 状态回流**。

### 11.2 为什么是「组织条线 × 场景」，不是只有场景

研发、业务、HR 讨论的问题不同，该写回的系统不同，黑话也不同。  
只有 Scenario 没有 OrgDomain，会出现「用研发词表硬解 HR 会」或「业务结论写成技术缺陷单」。

### 11.3 为什么词表必须分桶

全行一张词表会制造跨域同词异义（都叫「灰度」却不是一个意思）。  
分桶 + 跨域消歧，才是多人协作下的可懂性工程。

### 11.4 为什么不用一套万能总结 Prompt

技术方案评审、业务活动复盘、绩效校准的成功标准完全不同。  
差异必须是数据化的 Profile，而不是藏在 Prompt 里。

### 11.5 为什么深嵌入默认要确认（HR 更严）

写回可能触发缺陷单、发布、甚至 HR 流程；误写成本高。  
确认是核心链路约束，不是体验减分。

### 11.6 为什么先 Connector SPI，再逐部门接入

V1 证明嵌入契约；部门系统接入是增长，不是内核返工。

### 11.7 为什么 Understanding 独立且按域加载词表

黑话按部门分裂。独立门槛 + 分域加载，才能挡住「装懂后建错单」。

### 11.8 为什么多 Agent + 管理者拓扑

预订、分域理解、产物、嵌入风险不同；需要闸门。去中心互聊不适合银行写回。

### 11.9 为什么 V1 不做会中实时语音

另一复杂度主轴；与条线嵌入抢注意力。预留即可。

### 11.10 为什么 Greenfield

preview 只能堆补丁；要「分条线嵌入工作」，必须换骨架。

## 14. 风险与对策

| 风险 | 对策 |
|------|------|
| 行内系统接口难协调 | 先 SPI + mock；主路径只硬接 1 个 Connector |
| 听不懂却自动建单 | embed_gate；未知术语/低置信默认 block/confirm_only |
| 全行词表污染 / 跨域同词异义 | glossary 分桶；跨域歧义强制确认；评测锁隔离 |
| 场景配置腐化成第二套代码 | OrgDomain×Scenario 数据化 + 评测锁字段；禁止散落 if-else |
| HR/敏感内容误投递 | hr 域默认高敏；最小必要分发；写回强 HITL |
| 权限与检索打架 | Domain 检索强制 ACL；只注入本场 glossary_scopes |
| 外部 API 不稳 | 超时重试、半成功、用户可见、补偿任务 |
| 范围膨胀到实时会中/一次接完所有部门 | 架构评审拒绝；Connector/词表按部门排队 |
| 旧代码人情债 | 只接受过评测的移植 |
