## 一、JUC

### Q1：ThreadLocal 的内存泄漏问题

**A：**

一句话结论：ThreadLocal 不是“弱引用就一定不泄漏”，真正容易泄漏的是 **value**。
原因是 ThreadLocalMap 里 key 是弱引用，但 value 是强引用。ThreadLocal 被回收以后 key 变 null，可 value 还挂在 Entry 上；只要线程不结束（线程池线程会一直活着），value 就可能一直下不去。

怎么规避？最稳的就是用完显式 `remove()`，别指望 GC“顺带帮你清”。线程池场景更要注意，不然还会出现“串数据”（下一个任务读到上一个任务的 ThreadLocal）。
我们项目里 traceId 就是走 ThreadLocal 传递的，请求进来时 set，出请求时 remove，线程池场景必须显式 remove 否则会串数据。

### Q2：ConcurrentHashMap 的 transfer 过程

**A：**

Java 8 的 CHM 扩容核心是“大家一起搬”，不是某一个线程独占搬家。
触发扩容的线程会开始迁移，其他线程在 put 的时候如果发现正在扩容，也会 `helpTransfer` 帮着迁一段。
迁完的桶会放一个 ForwardingNode，占位告诉后续读写：去新表找。

关键点：迁移是按桶粒度锁的（synchronized 只锁单桶），所以扩容期间不是全表卡死。

落到项目上，如果面试官问“你用 CHM 干过啥”：我在项目一做规则缓存时用过，典型读多写少的场景，写是异步刷新，读并发很高。

### Q3：CompletableFuture 链式超时的正确写法

**A：**

这题我会先提醒一个坑：`orTimeout` 是给“整条链”加截止时间的，不是给某一步单独加。
如果你想“每一步都有自己的超时”，要么每个 future 自己配超时，要么用 `completeOnTimeout` 给默认值。

在我们项目里（类似项目二那种并发下游编排），做法是：
- 整条链路有一个总截止（比如比 SLA 略短）
- 每个下游也有各自超时，超时后直接降级成默认值

典型写法就是 `orTimeout + exceptionally`，但 `exceptionally` 里别写阻塞逻辑，不然你又把异步变回同步了。

---

### Q4：AQS 独占/共享两种模式的区别

**A：**

独占/共享我会用一句话区分：
- **独占**：同一时刻只能一个线程拿到（ReentrantLock）。
- **共享**：同一时刻可以多个线程一起拿（Semaphore/CountDownLatch）。

实现上就是 AQS 的 `state` 含义不同：独占通常是 0/1（或重入计数）；共享更像“剩余许可数”。

项目里我用得更多是黑盒：CountDownLatch 做并发测试同步，Semaphore 做并发度控制。AQS 的更深细节主要来自我看源码，不会硬说成线上踩坑。

## 二、JVM / GC

### Q5：G1 vs CMS，生产怎么选？

**A：**

我回答这题一般先给结论：现在大多数生产场景我优先选 G1，CMS 基本是“老项目遗留”。

CMS 的特点是并发标记清除，但会有浮动垃圾，堆一大、Full GC 一来 STW 就很难看；堆越大越明显。
G1 从 JDK9 起就是默认，更适合大堆场景（8G+），它按 Region 管理，能通过 `MaxGCPauseMillis` 做停顿目标控制，一般不会出现 CMS 那种突然几秒的 Full GC。
落到我们项目：风控服务堆大小 **6G**，用的是 G1，原因很简单——接口 SLA 卡得死，不太能接受长停顿。
ZGC 的话，如果你是极低停顿（个位数毫秒）且愿意付出更多 CPU 成本，可以考虑，但要看业务取舍。

### Q6：OOM 排查流程

**A：**

我一般按“四步走”，面试官也容易跟上：

第一，确认 OOM 类型——看异常信息：`heap space` 是堆内，`Direct buffer memory` 是堆外，`Metaspace` 是元空间，`unable to create native thread` 是线程数超限，不同类型排查方向不同。

第二，抓 Heap Dump——用 `-XX:+HeapDumpOnOutOfMemoryError` 在 OOM 时自动生成，或者在高内存时手动 `jmap -dump`。

第三，用 MAT 分析——看 Dominator Tree 找大对象持有者，用 Path to GC Roots 找为什么没被回收，看 Leak Suspects 看 MAT 的自动诊断。

第四，判断是泄漏还是堆积——泄漏特征是内存单调增长、GC 后不下降；堆积特征是跟流量正相关、峰后会回落。处置方案不同：泄漏需要修复代码，堆积需要优化处理速度或扩容。

这个流程我在项目一实际跑过，最后定位到的是 Direct Buffer 堆积（更像高峰积压），不是典型泄漏。

## 三、Redis

### Q7：缓存穿透 / 击穿 / 雪崩区分

**A：**

穿透：查询的 key 根本不存在（既不在缓存也不在 DB），每次都打到 DB。解法：空值缓存（设短 TTL）或布隆过滤器拦截非法 key。

击穿：某个热点 key 过期的瞬间，大量请求同时穿透到 DB。解法：互斥锁（只有一个请求去查 DB 重建缓存，其他等待）或热点 key 不过期（定时异步刷新）。

雪崩：大量 key 同时过期，导致请求同时打 DB。解法：过期时间加随机 jitter，分散过期时间。

项目二的场景：黑名单查询是热点 key，用了本地缓存 + Redis 双层缓存，本地缓存兜住了 Redis 偶尔击穿的风险。

---

### Q8：Redis 单线程 + IO 多路复用为什么够快？

**A：**

Redis 的速度主要来自两个方面：第一是纯内存操作，读写比磁盘快几个数量级；第二是避免了多线程的锁竞争开销——单线程处理命令，不需要加锁，CPU cache 命中率高。

IO 多路复用（epoll）解决的是'连接多'的问题：一个线程可以同时监听几万个连接的事件，不需要每个连接一个线程。这解决了 C10K 问题（高并发连接），但每个命令的处理还是顺序的。

单线程的瓶颈：CPU 密集型命令（如大 SORT、KEYS *）会阻塞所有请求。Redis 6.0 引入了 IO 多线程（Network IO 用多线程，命令执行还是单线程），缓解了网络 IO 的瓶颈。

## 四、RocketMQ

### Q9：消息幂等性怎么做？

**A：**

分两层。第一层，RocketMQ 的 at-least-once 保证：消息可能重复投递，消费者必须保证幂等。第二层，业务层幂等：用唯一消息 ID 或业务唯一键，在处理前先查数据库或 Redis 里是否有处理记录，有则跳过，没有则处理后写入记录。

幂等记录的存储：用 Redis SET NX + TTL 实现分布式锁式幂等检查，TTL 设为消息最长可能被重试的时间。

顺序消费场景：只有绑定到同一个 MessageQueue 的消息才能保证顺序，同一业务 ID 的消息要路由到同一个 MessageQueue（通过 hashKey）。

---

### Q10：消息积压怎么处理？

**A：**

积压分两种情况。第一种，消费者性能不足：扩消费者实例（受 MessageQueue 数量限制，实例数不能超过 Queue 数）或者优化消费端处理逻辑（异步化、批量处理）。第二种，突发流量导致短暂积压：临时扩容消费者 + 优先处理高优先级消息。

应急方案：如果积压严重且当前的 Topic MessageQueue 数不够，可以建一个新 Topic 把消息导过去，新 Topic 设置更多 Queue 分区，用临时消费者快速消费。

我们项目二的事件流就是 RocketMQ：登录/交易事件发到 Topic，Flink 消费做特征预计算，消费端做幂等和顺序消费。

## 五、MySQL

### Q11：MVCC 读的可见性规则

**A：**

核心是**版本可见性判断**。每个事务启动时会分配一个 transaction id，生成一个 ReadView，ReadView 记录了'当前活跃事务 ID 列表'。对于某一行的某个版本，可见性规则是：如果这个版本的创建事务 ID 比我的事务 ID 小，且不在活跃事务列表里，说明这个版本已经提交，我可以看到；如果创建者是我自己，也可以看到；否则找 undo log 的上一个版本继续判断。

RR 和 RC 的区别：RR（Repeatable Read）在事务开始时生成一次 ReadView，整个事务看到的快照是一致的；RC（Read Committed）在每次读时生成新的 ReadView，所以能读到已提交的最新版本（可能每次读结果不同）。

当前读（select for update、update、delete）：绕过 MVCC，直接读最新版本并加锁。

## 六、Netty / 设计题

### Q12：如果让你设计一个百万连接的长连接网关，你怎么做？

**A：**

这类设计题我会分四层来说。

第一层，连接接入：Netty 作为接入层，Boss group 接受连接，Worker group 处理 IO，根据 CPU 核数配置 Worker 数，保证 EventLoop 不被阻塞。心跳机制用 IdleStateHandler 检测空闲连接，定时清理死链。

第二层，连接管理：用 ConcurrentHashMap 维护 connectionId 到 Channel 的映射。百万连接不能每个 Channel 都独立定时器，要用 HashedWheelTimer 批量管理。内存控制是关键，每个 Channel 持有状态要尽量小。

第三层，业务隔离：业务逻辑 offload 到独立线程池，不在 EventLoop 里做。IO 密集型和 CPU 密集型业务分别用不同线程池隔离，防止互相影响。

第四层，运维保障：连接数、消息延迟、EventLoop 等待时间纳入监控；接入层无状态，方便水平扩容；热发布不断连（我们用的是滚动发布：先摘掉一台流量，等连接自然断开后再发新版本，发完再挂回，逐台滚动）。

## 七、Flink / 实时计算（新版简历高频）

### Q13：为什么要引入 Flink？不用在线现算行不行？

**A：**

我会先讲结论：引 Flink 的目的不是“追新技术”，而是把**时序/窗口类特征**从在线链路里挪出去，让在线接口只做“取特征 + 规则计算”，这样 P99 更稳。

如果在线现算，你要么同步查很多下游，要么自己在服务里维护状态，尾延迟都会变得不可控，而且扩容/重启时状态一致性也会变差。

Flink 这条链路的代价是运维复杂度上升，所以我会强调我们用 Shadow Mode/灰度门禁把风险压住：先影子验证，达标再生效。

### Q14：事件时间、水位线、Checkpoint 这三个你怎么解释？

**A：**

- 事件时间：按“事件发生的时间”算窗口，适合乱序/延迟的风控事件流。
- 水位线：表达“我最多等多久的迟到”，超过这个阈值的迟到要么丢弃要么走补偿逻辑（我们 allowed lateness 设 30 秒，迟到超过的进侧输出或丢弃）。
- Checkpoint：把状态和消费进度做一致性快照，任务挂了能从确定位置恢复。

面试官追问“恢复后会不会重复输出”，我会回答：要么 exactly-once 语义，要么 at-least-once + 幂等（写 Redis/落明细都要带幂等键/版本号）。

### Q15：CEP 链式欺诈识别怎么做？怎么避免状态膨胀？

**A：**

CEP 我会按“模式 + 窗口 + 状态约束”讲清楚，然后强调命中后要输出“命中路径 + 上下文”，这样才可审计、可复盘。

状态膨胀主要靠三件事：state TTL、超时清理、以及按 key 维度限界（必要时分层/采样）。不做这三件事，长窗口 + 高基数 key 很容易把状态打爆。
