# 03｜答案：企业智能会议 Agent 平台（纪要君）

> 口语化第一人称，每题控制在 60~120 秒内说完。⚠️ 标注处需替换为你自己的真实数据。

---

## 开场 30 秒

纪要君是我们内部的会议智能助理，底层是 LangGraph + DeepSeek API。
我做的事情可以概括成一句话：**把 Demo 做成能上线、能管、出了问题能追责的系统**。
主要难点就三块：
- 高风险操作怎么防误触发（HITL）
- 外部模型/工具链不稳定怎么兜住（幻觉治理、序列修复）
- 超长会议纪要怎么分片再合并
最后的结果是：高风险操作（创建/修改/取消）我们做到全链路可审计；纪要能自动生成并发送；工具链路稳定性明显比早期好，同等业务量下 token 消耗比改造前降了约 **28%**。

## Q1：置信度阈值路由怎么设计的？置信度是怎么得到的？

**A：**

意图识别我们是让 LLM 直接做，但我会把输出“框死”：用 structured output 让它必须吐 JSON（意图类别 + 一个 0~1 的置信度）。
不靠 logprobs，主要是不同模型支持不一致，而且线上不稳定。

我也会坦白说：这个置信度不是严格概率，是“模型自我感觉”。但我们拿它做路由够用——我们关心的是它能不能把“我很确定”和“我不太确定”区分出来。

阈值按风险分层：修改/取消这种高风险，阈值就设高一点，宁可多问一句确认；查询/闲聊阈值可以低。原则就一句：**误触发的代价 > 多问一次的代价**。

---

## Q2：各意图阈值怎么调优的？有测试集吗？

**A：**

有测过，不然阈值就是拍脑袋。
样本来源一半是内部真实对话（做脱敏），一半是我自己补的“刁钻 case”，比如：
- 模糊表达：“帮我挪一下下午的会”
- 多意图混在一起：“把三点的会取消，顺便查一下明天有没有空”

调的时候我不会追“总体准确率最高”，高风险意图更在意的是**误触发尽量接近 0**。宁可多问一句确认，也不能误取消会议。
我们测试集大概 **200 条**（含真实对话脱敏 + 边界 case），高风险意图误触发率压到接近 0，整体准确率约 **92%**。

---

## Q3：低置信度降级后系统做什么？

**A：**

低置信度我就不让它“动手”了。
它会退回到一个澄清节点，直接问一句更具体的确认，比如：“你是要新建会议，还是改/取消已有会议？”——让用户把意图说清楚。

这里我会强调边界：降级不是“啥也不干”，是**主动把问题问清楚**。
体验上多一步确认，但换来的是不误操作。我们也会看降级后的重试率/澄清命中率，反推哪些表达最容易歧义，再去优化 prompt。

## Q4：Checkpointer 多模式存储，各模式适用场景是什么？

**A：**

我把它理解成“按环境选存储”，不复杂：
- **内存**：本地开发/单测，快，重启就丢状态也无所谓。
- **SQLite**：单机部署/演示环境，用一个文件就能跑起来，不额外依赖。
- **MySQL**：生产，多实例共享状态，才能做到跨实例会话恢复（用户断线/换机器还能接着走）。

存的东西也很工程化：当前跑到哪个节点、必要的历史对话、等待用户确认的结构化参数（HITL），以及已经执行过的 tool 调用记录（用来保证恢复时不重复执行）。生产用的是 MySQL 模式，支持多实例共享状态。

## Q5：跨会话恢复的幂等性怎么保证？重放会不会重复预订？

**A：**

这块我会很明确：不做幂等就不敢做恢复。

做法是每次工具调用都带一个幂等键（会话 ID + 操作类型 + 目标资源），外部系统（比如腾讯会议 API）那边如果支持也会一起校验。
恢复时先看我们状态里有没有对应的 tool result：
- 有结果：说明之前已经执行过了，直接复用结果，不再重发。
- 没结果：才会重试一次（通常是中途崩溃导致“发出去了但结果没落库”）。

多端并发这类极端情况，我们用乐观锁/version 防御，保证同一会话同一时刻只允许一个写入成功。

## Q6：HITL 审批阶段，用户说"改到明天下午"，怎么处理？

**A：**

我不会让它回到“重新识别意图”那一套，确认阶段就专门做**参数修订**。
用户说“改到明天下午”，我们把它当成对现有参数的 patch：
- 先用 LLM 解析这句话，提取变化的字段（日期/时间）
- 只覆盖用户提到的字段，其他字段保持不动
- 合并后做一次校验（时间合法、是否冲突等）
- 再把更新后的参数展示给用户确认

这个体验上更像“你改哪我就改哪”，不用用户重说一遍所有参数。
支持多轮修订，直到用户说“确认”为止。

## Q7：超长会议纪要怎么分片和合并？

**A：**

我们用的是 Map-Reduce，而不是 Refine。
原因很实际：Refine 串行，前一段总结的误差会一路传下去；Map-Reduce 是并行总结后再合并，错误不容易“连锁放大”，速度也更快。

分片就按 token 预算切，尽量在段落/发言人边界切，避免把一句话切断。
如果遇到“单段就超长”的极端情况，就递归再切一层。

合并阶段把每段的 summary 拼起来，再跑一次合并 prompt，抽关键议题/决策/行动项，输出最终结构化纪要。

## Q8：幻觉检测的判断标准是什么？如何区分"真调了但没结果"和"根本没调"？

**A：**

我不靠“感觉”，优先用 API 结构来判断。
最硬的证据就是：assistant message 里有没有 `tool_calls`。
- 有 `tool_calls`：说明它确实发起了工具调用请求。
- 没有 `tool_calls` 但嘴上说“已创建成功”：这基本就是幻觉。

再细分一下：
- 有 `tool_calls` 但 tool 返回 error：这叫“真的调了，但失败了”，走正常错误处理/重试。
- 没有 `tool_calls` 但声称成功：走补执行。

LLM 自检我只当兜底（让模型评价自己也可能不准），主要还是靠结构化信号。

---

## Q9："提取参数补执行"是怎么做的？

**A：**

流程很直：发现幻觉 → 从历史里把参数抠出来 → 真正去调工具。

参数提取我会先规则后 LLM：
- 能规则提的先规则提（时间、地点、会议主题这类），稳定、可控。
- 实在提不到再用 LLM 兜底做语义抽取。

补执行前一定做幂等检查：先看有没有 tool result，避免重复执行。
补执行成功率我们实测在 **85%** 左右，漏执行导致的用户重发约减少 **80%**。

为啥不让模型“再生成一次 tool call”？因为幻觉场景下模型可能还会继续自信地“以为自己做了”，反而更不稳；规则提参更确定。

## Q10：序列修复和安全截断怎么做？

**A：**

这块踩坑很多，我一般用一句话描述：**tool_calls 和 tool_result 必须成对**。
不能出现“悬空的 tool_calls 没结果”，也不能出现“只有 tool_result 没调用”。否则 API 直接报错。

所以我们每次请求前会做两步：
1) **序列修复**：扫描历史，找到不完整的配对，截断到最后一个完整配对。
2) **安全截断**：历史太长就保留 system + 最近 N 轮，丢中间；但丢的时候也要按配对一起丢，不能拆散。

这两步做完，调用稳定性就提升很多。

## Q11：模型调用成本下降怎么量化？

**A：**

我量化的是“同等业务量下的 token 消耗”。
改造前两块最浪费：
- 序列不合法 → API 报错 → 修复后重试（带全量 history 重发，token 直接翻倍）
- 幻觉导致工具没执行 → 用户重发 → 又一轮对话

改造后序列报错基本消失，幻觉漏执行也能自动补执行，用户不需要重发，所以 token 消耗就下来了。
改造前同等业务量下 token 消耗约 **日均 120 万**，改造后降到 **约 86 万**，下降约 **28%**。

## Q12：为什么安全部门做会议 Agent？数据出境怎么合规？

**A：**

两个原因。
第一，安全部门天然在意“留痕、可审计、权限管控”。会议这类工具一旦做大，谁创建/谁改/谁取消、纪要怎么生成，都要能追溯，这跟安全审计的诉求很一致。
第二，这是内部效率工具，不直接面向外部客户，合规边界相对清晰，适合作为 AI 工程化落地的场景。

合规上我们做得很保守：调用外部 API 前，对 prompt 里的 PII 做脱敏（人名匿名化、电话邮箱屏蔽、内部项目名泛化）。会议内容/纪要原文只在内部系统存，不直接把原文送出去。
我们内部有数据出境审批流程，调用外部 API 前需经合规审批；长期计划是私有化部署，现阶段是公有云 API + 严格脱敏。
私有化部署是我们长期方向，现阶段是公有云 API + 严格脱敏这套组合。
