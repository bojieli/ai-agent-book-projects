#### 2.5.2 参照 DeepAudit 架构的差距分析

DeepAudit-3.0.0 是一个多 Agent 代码安全审计系统，技术上与纪要君高度同类（都是 LLM + 工具调用 + 多 Agent 编排），其工程能力可作为对标参考。

**DeepAudit 有而简历中未体现的工程点：**

| DeepAudit 工程能力 | 简历中对应情况 | 建议 |
|---|---|---|
| **熔断器（CircuitBreaker）** 防止工具调用级联失败 | 无 | 可在"工具调用稳定性"中补一句"对高频工具调用设计熔断降级机制" |
| **指数退避重试（ExponentialBackoff）** | 无 | 可归入"幂等控制"条目，补一句"重试机制+幂等键" |
| **速率限制（RateLimiter）** 防止 LLM 调用过频 | 只提"成本明显下降" | 成本治理可展开为"模型调用速率控制+分层路由（简单任务走小模型）" |
| **执行上下文追踪（ExecutionContext）** 带 trace_path | 无 | 可补"工具调用链路可追踪、可复现" |
| **检查点间隔策略（每5轮保存）** | 只说"状态持久化" | 可补"支持以 checkpoint 粒度恢复，避免长链路全量重放" |
| **ReAct 循环（Thought-Action-Observation）** | 隐含在"意图识别→路由→处理"中 | 可明确描述为"决策循环"，体现 Agent 推理能力 |

**建议在项目三中补充的表述（可选，选1~2条即可）：**

```
* 针对 LLM 调用和外部工具调用的可靠性，
  建设熔断降级、指数退避重试与速率控制机制，
  防止单点工具失败导致整条链路中断；
  通过模型分层路由（复杂任务走强模型、简单任务走轻量模型）
  实现成本与效果的平衡。

* 会话状态以 checkpoint 粒度持久化，
  支持从任意中断点恢复执行，
  避免长链路任务全量重放；
  工具调用记录附带执行上下文与追踪路径，
  支持失败定位与链路复现。
```

**目前简历中项目三独有、DeepAudit 没有的亮点（需要保留）：**

- **HITL（Human-in-the-Loop）确认**：DeepAudit 是全自动审计，纪要君有 HITL 是企业场景的核心差异化，必须保留且突出。
- **自然语言参数修订**：用户在确认阶段用自然语言修改参数并触发重新规划，这是纪要君特有的交互设计。
- **会后代办闭环**：纪要君抽取行动项→结构化代办→分发跟踪，这是比 DeepAudit 更完整的"端到端价值"体现，P6+ 新版已经补入，是加分项。

### 逐条说明

#### 🔴 项目一：核心工作第一条与背景重复

背景结尾已经说了：
> "通过'高危必采、中低危按策略抽样、全量离线兜底'的分层策略……"

核心工作第一条又重复了：
> "形成'高危必采、中低危抽样、全量离线兜底'的整体架构。"

背景说的是**决策**，核心工作应该说**落地**。建议核心工作第一条改为说明各数据源的差异化接入方式（WAF 旁路采集 / 管理台探针 / MQ 中间层），把架构策略的重复短语去掉。

#### 🔴 项目一：结果丢失了最有价值的业务陈述

当前结果：
> "相关能力已用于违规外传与异常行为审计场景，核心服务可用性达 99.99%"

原始版有这句：
> "持续拦截多起违规数据外传事件及管理台内部数据泄露风险"

"已用于某某场景"是说手段，"持续拦截了违规事件"才是价值。这是平台存在意义的直接证明，必须补回。

#### 🟡 两处"较好"过于保守

- 项目二结果：`决策链路具备较好的可追溯性与治理能力` → 建议改为`决策链路可追溯、可治理`
- 项目三结果：`高风险操作具备较好的可控性与可审计性` → 项目三原版写的是"全链路可控与可审计"，现在自己降级了

P6+ 不需要在这种地方主动打折。

#### 🟡 项目二 CEP 条：丢失了可信度最高的细节

原版：
> "命中后输出命中路径与关键上下文（设备/IP/金额等）用于处置与复盘"

现版：
> "支持多步行为序列识别与关键上下文输出"

括号里的 `设备/IP/金额` 是让面试官相信你真的做过这件事的细节，不是废话。建议补回字段举例。

#### 🟢 项目三成本下降无量化

> "模型调用成本明显下降"

"明显"在面试中必被追问。如果有精确数字最好；没有的话改成不可被挑刺的表述，例如：
> "通过模型分层路由与长文本分片，高成本模型调用次数可控"

#### 🟢 项目三工程能力条过于密集

> "状态持久化、checkpoint 恢复、幂等、序列修复与安全截断"

5 个概念平铺，每个都没有立体感。建议按"可恢复性 + 可靠性"两类合并压缩，例如：
> "负责会话状态持久化与 checkpoint 粒度恢复，以及工具调用幂等与消息序列健壮性治理"
