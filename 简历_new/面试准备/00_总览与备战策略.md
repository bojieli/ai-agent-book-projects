# 00｜总览与备战策略

> 本文件是所有模块的"入口地图"，先读这里，明确哪些点最高危、如何备证据。

---

## 0. 使用方式（把“问题清单”变成“可讲的答案”）

- **先背骨架**：每个问题都按同一个“答案骨架”回答（见下方 0.2）。
- **再补证据**：每个关键指标都准备“口径卡片”（见下方 0.3），避免被追问时失分。
- **最后做减法**：只记“必答/常问”，其余当加分项按需展开。
- **排障背 SOP**：把“压测/内存/CPU/网络排查”背成可执行步骤（见 `07_SOP_性能压测与故障排查.md`）。

### 0.1 标签说明（建议统一全库使用）

- **[必答]**：出现概率最高，不答会扣分
- **[常问]**：大概率会问到
- **[加分]**：讲得好会显著加分
- **[备选]**：除非面试官很钻或你主动引导

### 0.2 统一「答案骨架」（建议所有模块照这个讲）

按顺序讲，控制在 60～120 秒：

1) **一句话结论**：我做了什么/解决了什么约束  
2) **证据**：监控/日志/配置/压测对比（至少 1 条）  
3) **关键取舍**：为什么这么选，不选什么，代价是什么  
4) **风险与兜底**：失败时怎么降级/回滚/止损  
5) **复盘与演进**：改动后怎么验证不回退，下一步怎么优化

### 0.3 指标「口径卡片」模板（每个项目至少 3 张）

每个“数字/提升/可用性”都填这 6 项（不泄密也能讲清）：

- **指标名**：如 P99.99 / 平均 RT / 端到端延迟 / 可用性 / 成本
- **统计窗口**：活动期/日常/最近 30 天等
- **样本量**：请求量级/日志量级/过滤条件
- **是否含降级**：是否包含熔断降级/超时/失败重试路径
- **数据来源**：APM/Prometheus/日志平台/自研看板（说类型，不报内部域名）
- **对比基线**：改造前后各是多少，差值如何计算

## 一、最容易被追问 / 质疑的五大高危点

面试官通常在前 10 分钟就锁定以下方向，优先准备：

| 高危点 | 核心风险 | 对策 |
|---|---|---|
| **"主导/核心开发"的边界** | 面试官想知道你真正拍板/独立完成了什么 | 每个项目准备 1 个"是我决策的"关键设计点 |
| **指标口径是否站得住** | 数字太精确反而被怀疑，需要说清统计窗口、监控来源 | 每个数字准备 1 句"口径说明" |
| **关键词是否真做过** | 零拷贝 / Reactor 主从 / 内存池 / JVM 调优 / Lambda 架构 | 对应到具体配置、代码、改动前后对比 |
| **AI Agent 是否只是 Demo** | 工具调用稳定性、状态持久化、可量化效果是验真关键 | 准备真实的成功率/成本对比数据 |
| **三个项目"至今并行"** | 面试官担心你各项目只是挂名 | 说清当前精力分配比例，哪个在活跃迭代 |

## 三、面试最强「证据链材料」清单

> 原则：每一个"指标 / 收益 / 稳定性"都配一份可验证证据。面试官一旦感觉你能"拿证据说话"，会明显降低刁难强度。

### A）通用（所有项目都适用）
- **监控看板 3 张**：吞吐（QPS/吞吐量）、延迟（P95/P99/P99.99）、错误率（5xx/超时/降级命中）。
- **1 份压测报告摘要**：压测模型（并发、时长、数据量）、瓶颈点、优化前后对比。
- **1 份事故复盘摘要**：时间线、影响面、根因、修复、复发预防。
- **关键配置片段口述提纲**：超时、线程池、熔断/降级、限流、重试、缓存 TTL（无需泄密，能讲结构与取舍即可）。

### B）项目一（数据安全监测中心）
- **链路延迟证据**：端到端延迟分布（采集→接收→审计→告警）与高峰期曲线。
- **ES 索引与写入策略**：索引模板（mapping/分片）、bulk 写入参数、refresh 策略、冷热分层策略。
- **OOM/堆外内存证据**：Heap dump 关键结论（Dominator/GC Roots）或堆外内存增长证据（direct memory、ByteBuf 泄漏定位手段）。
- **规则热加载一致性**：规则版本号/灰度/回滚流程说明。

### C）项目二（业务安全平台 3.0）
- **P99 证据**：活动期/高峰期统计口径（窗口、样本量、是否含 Shadow/是否含降级路径）与对比图（简历口径 P99<150ms）。
- **Flink 正确性证据**：事件时间/水位线口径、Checkpoint 成功率与耗时、影子链路回放对账、反压与延迟指标。
- **CDC 下发与规则版本**：Aviator 规则入库、MySQL CDC 下发、版本一致性与回滚/灰度口径。
- **Shadow Mode 证据**：命中明细 ClickHouse 落库、误拦样本复核口径、达标后灰度生效与回滚流程。

### D）项目三（纪要君）
- **意图路由与状态机架构图**：LangGraph 的核心节点流转图、置信度阈值判定逻辑、Checkpointer 持久化机制。
- **纪要分片与合并总结 Prompt/代码摘要**：处理超长文本的 Map-Reduce 逻辑或 Prompt 片段，以及自动发送的异步任务代码结构。
- **幻觉治理与序列修复证据**：提取参数补执行工具的成功日志片段、处理 DeepSeek API 消息限制的截断修复逻辑。
- **模型调用成本下降量化**：改造前后 token 消耗对比（同等请求量下）、统计口径与时间窗口说明。

## 四、反向追问（你可以问面试官，用来加分）

- **系统现状**：当前最大痛点是吞吐、稳定性、成本、还是研发效率？有明确的优化指标吗？
- **工程化与安全**：对审计/合规/可观测性有什么硬性要求？（留痕、脱敏、权限、审批）
- **技术栈**：中间件选型（MQ、缓存、链路追踪、配置中心）与多活策略是什么？
- **团队协作**：你将负责的模块边界、与哪些团队对接、业务影响与上线流程如何？

## 五、面试官常用「让你现场做」的挑战题

### 让你画架构图（最常见）
请现场画出项目一端到端链路：WAF/管理台 → 采集 → 传输协议 → 接收服务 → 规则引擎 → 存储（ES/Hive）→ 告警 → 回溯查询。
- 追问：每段吞吐、延迟、失败重试、幂等键、监控指标分别是什么？

### 让你复盘一次线上事故（真实性验证）
挑一个你最典型的 OOM 或 P99/P99.9 延迟超标事故：时间线、告警、影响面、定位、修复、回滚、复发预防。

### 让你给出取舍（架构能力）
- 为什么项目一用 Hive + ES + 自研 Netty，而项目二又引入 Flink + ClickHouse？（约束不同：审计 vs 风控）
- 为什么不直接用 gRPC/HTTP，而要自研 TCP 私有协议？

### 让你落到代码级（实现能力）
- **Flink 指标口径**：事件时间/水位线怎么设？Checkpoint 成功率怎么看？出现反压怎么排？
- **Netty 粘包拆包**你怎么实现 decoder？LengthFieldBasedFrameDecoder 参数怎么配？
- **Shadow Mode** 怎么做“先验证再生效”？达标口径是什么？如何灰度切换与回滚？
