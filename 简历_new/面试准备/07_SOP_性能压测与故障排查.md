# 07｜SOP：性能压测与故障排查（面试可背版）

> 目标：把“我会排障/我做过压测”说成**可执行的步骤**。面试时你可以先用“30 秒讲法”，再按 SOP 展开细节。

---

## 0. 通用方法论（所有故障都适用）

### 0.1 30 秒讲法（先背这一段）

我一般按 **“先止血，再定界，最后定位与复盘”**：

- **止血**：先把影响面压住（限流/降级/熔断/扩容/回滚），保证核心链路先稳定。
- **定界**：把问题归到一类（CPU/内存/GC/线程池/网络/下游/DB/缓存），并确认是“应用内”还是“外部依赖”。
- **定位**：采集证据（监控、日志、线程栈、GC 日志、dump、火焰图、抓包），用证据排除法收敛到 1~2 个根因。
- **复盘**：把根因转成可防复发的动作（监控项、阈值、熔断策略、容量基线、Runbook）。

### 0.2 必备证据清单（现场别空谈）

- **时间线**：开始时间、峰值、恢复时间（把“因果链”串起来）
- **四大黄金指标**：QPS/吞吐、RT（P50/P95/P99/P999）、错误率、饱和度（CPU/内存/线程池/队列/连接池）
- **上游/下游对齐**：同一时间窗，哪个先抖（先抖的一侧通常更接近根因）
- **变更对齐**：发布/配置变更/灰度/依赖变更/流量变化

## 1. 性能压测 SOP（Capacity & SLA）

### 1.1 压测前：把“目标”和“口径”说清楚

- **SLO/SLA**：例如 RT P99 < 300ms，错误率 < 0.1%
- **流量模型**：均值/峰值、突刺、读写比、请求大小、下游依赖数量
- **统计口径**：平均 vs P95/P99/P99.99；窗口（高峰 10 分钟 / 自然日）
- **成功标准**：达标曲线 + 资源余量（CPU < 70%/队列不积压/GC 稳定）

### 1.2 压测环境：尽量“像线上”

- **部署拓扑一致**：实例数、核数、内存、JVM 参数、LB、超时/重试、线程池配置
- **依赖可控**：DB/Redis/MQ/ES 要么用线上影子，要么用可还原数据规模的预发
- **数据规模一致**：索引、表行数、缓存命中率、热点 key 分布（否则压测结论会偏）
- **隔离**：压测流量与真实用户隔离（灰度、影子库、专用 Topic）

### 1.3 压测设计：四类测试缺一不可

- **Ramp（爬坡）**：从低到高逐步加压，找到拐点
- **Soak（长稳）**：在目标 QPS 下跑 1~4 小时，观察内存/句柄/连接是否“缓慢上涨”
- **Stress（极限）**：超出目标 1.5~3 倍，验证降级/熔断是否按预期触发
- **Spike（突刺）**：瞬时突增（比如 5s 内从 1 倍到 5 倍），看排队与恢复速度

### 1.4 压测过程：边压边看“饱和点”

每上一个台阶（比如 +10% QPS）就记录一次：

- **RT 分位数**：P50/P95/P99/P999
- **错误率**：超时、5xx、业务错误码
- **饱和度**：CPU、load、GC（频率/停顿）、线程池活跃数、队列长度、连接池等待
- **依赖侧**：DB 慢 SQL、Redis 延迟、MQ 堆积、ES 写入延迟

判断瓶颈常用信号：

- CPU 先满：计算/序列化/锁竞争/上下文切换
- RT 先涨但 CPU 不满：排队（线程池/队列）、下游慢、网络抖动
- 错误率先涨：超时设置不合理、连接池耗尽、下游熔断未配置

### 1.5 压测产出物（面试官最爱问）

- **容量结论**：单机/集群最大稳定 QPS（达标 RT+错误率），以及安全余量
- **瓶颈定位**：Top1/Top2 瓶颈 + 证据（图、火焰图、慢依赖 TopN）
- **优化闭环**：优化项 → 复压 → 曲线改善（写 1~2 个最有力的对比数据）
- **压测脚本/用例**：可复现（Runbook）

## 2. 内存泄漏 / 内存持续上涨 SOP

### 2.1 先定类型：是哪一种“内存”在涨？

从现象把问题归类（不同类型工具不同）：

- **Java 堆（heap）**：`OutOfMemoryError: Java heap space`
- **堆外（direct / native）**：`OutOfMemoryError: Direct buffer memory` 或 RSS 持续涨但堆不大
- **元空间（metaspace）**：`OutOfMemoryError: Metaspace`
- **线程过多**：`unable to create new native thread`

### 2.2 快速止血（先把服务救活）

- **限流/降级**：先压住请求量，避免继续扩大占用
- **重启策略**：必要时滚动重启（同时保留现场证据），别“重启治百病”不留证据
- **降低缓存/队列上限**：有界队列/连接池/缓冲区上限先收紧，避免无限堆积

### 2.3 证据采集（一次抓齐，别来回折腾）

- **JVM**：GC 日志、`jstat -gcutil`、`jcmd VM.native_memory`（如果开了 NMT）
- **线程**：`jstack`（看是否存在大量 WAITING/阻塞/线程泄漏）
- **堆 dump**：高水位时抓 `heap dump`（MAT 分析）
- **堆外/Netty**：direct memory 指标、池化 allocator 指标、队列积压指标

### 2.4 定位流程（面试可讲“证据链”）

1) **确认是泄漏还是堆积**  
   - 泄漏：内存单调上涨，GC 后不回落  
   - 堆积：跟流量相关，峰值后会回落

2) **堆内泄漏**（Heap Dump + MAT）  
   - 看 Dominator Tree 找“大户”  
   - 看 Path to GC Roots 找“谁在引用它”  
   - 最后把引用链落到代码结构（缓存/集合/静态 Map/ThreadLocal）

3) **堆外泄漏/增长**  
   - 看 direct memory、ByteBuf、NIO buffer、JNI、文件句柄  
   - Netty 场景可临时提升 leak detector（上线谨慎，性能有损）定位未释放 ByteBuf

### 2.5 常见根因模板（你可以套你自己的项目）

- **无界队列/积压**：下游变慢 → 队列堆积 → buffer/对象引用不释放
- **缓存未设上限/TTL**：本地缓存/Guava/Caffeine 未限容
- **ThreadLocal 未 remove**：线程池复用导致 value 常驻
- **连接/句柄泄漏**：HTTP 连接未关闭、文件句柄未释放

### 2.6 修复与防复发

- **有界化**：队列/缓存/连接池都要上限 + 告警
- **可观测**：direct memory、队列积压、缓存大小、拒绝次数都要监控
- **压测回归**：长稳压测看“是否缓慢上涨”

## 3. CPU 飙升 / Load 飙高 SOP

### 3.1 先止血（避免全量雪崩）

- 限流/降级/熔断，必要时扩容把影响摊薄
- 如果是发布引入，优先回滚/降级到稳定版本

### 3.2 定界：CPU 是“真忙”还是“假忙”

- **真忙**：CPU user 高（计算、序列化、正则、加解密、循环）
- **假忙**：CPU system 高（内核、网络、IO）、上下文切换高（线程过多/锁竞争）
- **GC 忙**：GC 时间占比高（频繁 GC 导致“看起来 CPU 很高”）

### 3.3 证据采集（推荐组合）

- **火焰图**：async-profiler / JFR（最直观）
- **线程栈**：连续抓 3 次 `jstack`（间隔 5~10s）找热点线程
- **系统侧**：top/htop、perf、上下文切换、run queue
- **应用侧**：APM Top 接口、慢依赖 TopN

### 3.4 定位套路（面试官追问也不怕）

1) 找出“吃 CPU 的线程/方法”（火焰图 Top）  
2) 判断是代码逻辑（死循环/大对象序列化/日志过量）还是锁竞争（BLOCKED 多）  
3) 如果是锁竞争：看锁对象、缩小锁粒度/换并发结构/降共享  
4) 如果是 GC：回到内存问题（对象分配过快、缓存失控）

### 3.5 常见根因与快速修复

- **日志过量**：热路径 info 打太多 → 先降级日志级别/采样
- **正则/JSON**：复杂正则/大对象序列化 → 先优化热路径或做字段裁剪
- **线程过多**：线程池参数不合理 → 限制最大线程/队列，避免抖动
- **缓存击穿**：命中率骤降 → 限流 + 热 key 保护 + 预热

## 4. 网络故障 / 超时 / 抖动 SOP

### 4.1 现象分类（先把问题说清楚）

- **连接失败**：connection refused / no route to host
- **超时**：connect timeout / read timeout / gateway timeout
- **重置**：connection reset by peer
- **延迟抖动**：P99/P999 突然拉高但错误率不一定高
- **DNS**：域名解析慢/失败（间歇性）

### 4.2 快速止血

- 调低重试（或加退避），避免重试风暴
- 对慢依赖熔断/降级，保护主链路
- 调整超时（connect/read 分开），避免“长时间卡住线程/事件环”

### 4.3 定界：是应用、是依赖，还是链路

按“从近到远”排查：

1) **应用内**：连接池是否耗尽？是否有大量 TIME_WAIT？是否有请求堆积？
2) **依赖侧**：下游错误率/RT 是否同步上升？是否有发布/扩缩容？
3) **链路侧**：LB（WeLB/VIP）、机房链路、DNS、NAT、网络抖动

### 4.4 证据采集

- **客户端指标**：连接池等待时间、超时占比、重试次数、失败原因分布
- **服务端指标**：accept 队列、连接数、线程池/事件环是否被阻塞
- **链路工具**：ping/mtr/traceroute、tcpdump 抓包（看重传/握手/断连）
- **LB/网关**：5xx/超时/连接复用情况（如果能拿到）

### 4.5 常见根因模板

- **连接池耗尽**：超时设置过长 + 并发高 → 等待堆积
- **重试风暴**：下游慢 → 上游重试 → 放大流量 → 全链路雪崩
- **DNS 抖动**：解析慢导致 connect 慢
- **半开连接**：长连接没心跳/无 keepalive

### 4.6 修复与防复发

- **超时分层**：connect/read/overall deadline 分开；全链路要有总截止
- **重试有纪律**：只对幂等请求重试 + 指数退避 + 上限
- **熔断降级**：慢调用比例/异常比例；半开探测参数可解释
- **演练**：用 `tc/netem` 做丢包/延迟注入（预发环境），验证系统能“稳态退化”

## 5. 版本上线与回归压测 SOP（发版不背锅）

> 目标：每次版本上线前，都能回答清楚“**我怎么证明这次不会把性能打崩**”。这套 SOP 既能讲给面试官听，也能落地执行。

### 5.1 发版前：性能“准入门槛”（PR/提测阶段就卡住）

- **变更分级**：先判断这次是不是“性能高风险变更”  
  - 高风险：序列化/协议、线程模型、缓存策略、SQL/索引、连接池/超时/重试、GC/JVM 参数、限流/熔断策略、依赖版本升级  
  - 低风险：纯文案、非核心路径逻辑、配置不影响主链路
- **性能预算（performance budget）**：提前写明允许的退化范围  
  - 例如：P99 不得回退 > 5%，CPU 不得回退 > 10%，错误率不得上升
- **最小性能用例（micro-regression）**：至少有 1~3 条“核心接口”基准用例  
  - 固定输入、固定依赖 mock/影子、固定并发（例如 50/200/500 并发）

### 5.2 预发/灰度前：回归压测怎么做（和容量压测不同）

回归压测不是为了找“极限 QPS”，而是为了回答“新版本 vs 旧版本有没有退化”。建议做 **A/B 对比**：

- **基线版本**：当前线上稳定版本（old）
- **候选版本**：本次待发布版本（new）
- **对比口径**：同一流量模型、同一数据规模、同一机器规格、同一依赖版本

**执行步骤（推荐顺序）**：

1) **冒烟压测（5~10 分钟）**：小流量跑通 + 看错误码分布（先排功能/配置坑）  
2) **基准压测（15~30 分钟）**：目标 QPS（或目标并发）下看 P95/P99、CPU、GC、线程池/队列  
3) **长稳压测（30~120 分钟）**：看“缓慢上涨”（内存、句柄、连接数）  
4) **突刺（Spike）**：验证新版本在突增下是否更容易排队/超时

**判定规则（建议写死在发布单里）**：

- RT：P99/P999 不超过基线 + 5%
- 错误率：超时/5xx 不超过基线 + 0.1%
- 饱和度：CPU、线程池队列、连接池等待、GC 停顿不出现“新版本特有的拐点”

### 5.3 上线方式：灰度 + 门禁（Gating）+ 自动回滚条件

**灰度策略**（从小到大）：

- 1%（观察 10~30 分钟）→ 10%（观察 30~60 分钟）→ 50% → 100%  
  观察窗口按业务峰谷调整：尽量覆盖一个“相对忙”的时间段

**门禁指标（触发即暂停/回滚）**：

- **RT 分位数**：P99/P999 突然抬头且持续 5 分钟
- **错误率**：5xx/超时上升超过阈值
- **饱和度**：CPU 持续 > 75%，线程池队列持续积压，连接池等待时间飙升
- **依赖异常**：某下游错误率/RT 同步上升（警惕“新版本放大下游压力”）

**回滚决策**（一句话模板，面试官爱听）：

> 只要“核心指标持续退化 + 排除外部流量/依赖抖动”，我会优先回滚版本，而不是硬扛优化。

### 5.4 上线后：验证清单（把“我上线很稳”说成步骤）

- **对齐基线**：上线前 30 分钟 vs 上线后 30 分钟，对比同口径指标
- **慢请求 TopN**：看新版本是否出现新的慢路径
- **资源曲线**：CPU、GC、内存、连接池、队列，是否出现新拐点
- **业务监控**：核心业务成功率、拒绝/降级命中率是否异常

### 5.5 怎么判断“系统无故障/系统是健康的”（灰度验收标准）

> 面试时一句话：我不会凭“感觉”说没故障，我会按 SLI/门禁做验收，满足“无告警 + 指标不退化 + 无积压 + 资源不异常”才继续放量。

把“无故障”拆成 4 类可验证的信号（每次灰度阶段都跑一遍）：

1) **无告警（Alert）**  
   - 本服务：核心告警（错误率、超时、RT P99/P999、线程池队列、连接池等待、GC 停顿）在观察窗口内不触发  
   - 依赖侧：关键下游（DB/Redis/MQ/ES/外部 API）无同步异常告警  
   - 说明：有告警不一定是故障，但一定要能解释“是不是我这次发布引入的”

2) **指标不退化（SLI/SLO）**  
   - RT：P99/P999 与灰度前基线相比不超过 5%，并持续稳定（不是短暂尖刺）  
   - 错误率：超时/5xx/业务失败率不超过 0.1%  
   - 业务 KPI：核心成功率/通过率/命中率等不出现“新版本特有的偏移”

3) **无积压（Backlog/Queue）**  
   - 线程池队列：无持续增长（能在短时间内回落）  
   - MQ：无持续堆积（Lag 不持续上升）  
   - ES/DB：写入延迟不持续累积  
   - 说明：很多“看起来没报错”的问题，本质是“积压在变大”，一旦放量就爆

4) **资源不异常（Saturation）**  
   - CPU：不出现持续跑满或“新拐点”（同 QPS 下 CPU 明显更高）  
   - 内存：不出现“缓慢上涨不回落”（泄漏/堆积信号）  
   - GC：停顿时间/频率不出现显著恶化  
   - 连接：连接池等待、TIME_WAIT、FD 等不异常

**建议的验收节奏（更像线上实操）**：

- 每次放量后先看 **5 分钟**（快速发现配置/功能类问题）  
- 再看 **20~30 分钟**（观察 RT/错误率是否稳定）  
- 最后看 **一个业务小周期**（例如 30~60 分钟，覆盖一个相对忙的窗口）  

如果四类信号都“稳定”，且对齐基线无明显偏移，就可以说“当前阶段系统健康，可以继续放量”。

### 5.5 影子流量/旁路压测（可选加分项）

如果公司有能力做影子流量（shadow traffic），可以这么说：

- 线上真实流量复制一份给新版本**旁路处理**（不落真实写，不影响用户）
- 对比新旧版本的 RT/错误/资源开销，提前发现性能回退与异常路径
- 旁路结果只做观测与告警，不参与真实决策（避免风险）

## 6. 面试加分：把 SOP 和你的项目绑上

你每类 SOP 准备 1 句“落地例子”，但不泄密：

- **压测**：我做过长稳压测，发现 direct memory 会缓慢上涨，最后定位到无界队列积压导致 ByteBuf 引用未释放
- **内存**：我遇到过 direct memory OOM，通过 MAT + 引用链发现 ByteBuf 被队列引用，后来做了有界化 + 降级
- **CPU**：我用火焰图定位到某段 JSON 序列化是热路径，优化后 P99 从 220ms 降到 160ms 左右
- **网络**：我把超时/重试做了分层和退避，避免重试风暴，并配合熔断保护主链路
