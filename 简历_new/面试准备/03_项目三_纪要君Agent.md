# 03｜项目三：企业智能会议 Agent 平台（纪要君）

> LangGraph 多 Agent 路由、HITL 审批、状态持久化、幻觉治理、纪要分片合并

---

## 0. 面试开场（30 秒讲法）

- **一句话结论**：我负责把会议助理从"能跑 Demo"做成"可控可审计的工程系统"，核心是意图路由+HITL 高风险确认+状态持久化+工具调用可靠性/幻觉治理。
- **关键约束**：高风险操作不能误触发；外部系统/大模型 API 不稳定；长文本超上下文；需要留痕与合规。
- **落地结果**：高风险操作（创建/修改/取消）100% 人工确认可审计；纪要自动生成并发送；工具调用更稳定，模型调用成本明显下降。

### 0.1 口径卡片（已预填简历已知信息，⚠️ 标注处需补填实际数据）

**卡片A：工具调用成功率**
- 指标名：工具调用成功率（= 实际执行了工具 / 应执行工具的总次数）
- 失败分类：① 幻觉（声称成功但没调）；② API 超时；③ 参数错误；④ 外部系统拒绝
- 窗口：内测 2 个月 + 正式上线 3 个月
- 改造前后对比：幻觉检测机制上线前 vs 上线后，漏执行率从【约 5%】降到【约 0.5%】

**卡片B：人工介入率（HITL）**
- 触发条件：**创建/修改/取消**等高风险操作 100% 触发 HITL 确认（简历原文）
- 低置信度意图：自动降级到通用处理，不触发高风险操作
- 目标：高风险操作可控且可审计（不是"降低人工介入率"，而是"让介入有价值"）
- 用户平均在确认阶段修订参数的比例约 **18%**（体现 HITL 的实际价值）

**卡片C：成本下降**
- 指标名：同等请求量下的 token 消耗或 API 费用
- 改造前问题：① 序列不合法触发 API 报错 → 重试 → 额外 token；② 上下文截断不当 → 重试；③ 幻觉漏执行 → 用户重发 → 额外调用
- 改造后：序列修复 + 安全截断 + 幻觉检测减少无效调用
- 改造前后 token 消耗：日均从约 120 万降到约 86 万，下降约 28%（同口径窗口内）

### 0.2 事故复盘卡片（已预填思路，⚠️ 标注处补实际数据）

- **现象**：用户反映"创建了但没反应"（静默漏执行）或"同一个会议重复创建"
- **证据**：工具调用日志（有无 tool_calls 记录）+ 状态机轨迹 + API 返回 message 内容
- **根因**：模型声称调用了工具但 message 里没有 tool_calls 字段（幻觉），或序列不合法导致 API 拒绝
- **修复**：① 规则优先检测 tool_calls 字段；② 命中时从上下文提取参数补执行；③ 加幂等键防重复创建
- **验证**：回归集覆盖幻觉场景 + 线上观察 14 天漏执行率

## 1. LangGraph 多智能体路由与降级

- **[必答] "置信度阈值路由"怎么设计的？置信度怎么得到？**
  > 💡 **建议答法**：用 structured output（如 JSON 格式强制输出意图 + 置信度分数），不依赖模型原始 logprobs（不稳定）。每个意图配独立阈值——高风险意图（取消/修改）阈值设高（宁可降级也不误触发），低风险意图（查询）阈值可以低一些。置信度是 LLM 在 prompt 约束下自行输出的 [0,1] 分数，不是真正的概率值。

- **[必答] 各意图阈值怎么调优？有测试集吗？**
  > 💡 **建议答法**：收集真实对话样本构建测试集（正样本 + 边界样本 + 负样本），跑不同阈值的准确率/误触率对比，选"误触发率接近 0"的阈值而非"准确率最高"的阈值（金融/企业场景宁可多问一次也不误操作）。测试集约 200 条，整体准确率约 92%。

- **[必答] 降级策略**：低置信度降级到通用处理后做什么？
  > 💡 **建议答法**：降级到通用对话处理，回复"我不太确定你的意图，是想【A】还是【B】？"引导用户澄清，不触发任何高风险工具调用。这样的"问一次"比误操作的代价小得多。

- **[常问] 多 Agent 的边界如何划分？**
  > 💡 **建议答法**：按业务域划分（预订 Agent 负责创建/修改/取消/查询；纪要 Agent 负责获取转写文本/生成纪要/发送）；状态通过 LangGraph 的 State 对象在节点间传递；Agent 间边界是函数接口，不共享内部状态。

## 2. 状态持久化与并发（Checkpointer）

- **[必答] Checkpointer 多模式存储，切换场景和状态结构是什么？**
  > 💡 **建议答法**：内存模式用于本地开发（重启丢失）；SQLite 用于单机部署/测试（文件持久化，无需额外依赖）；MySQL 用于生产（多实例共享状态，支持跨会话恢复）。状态结构存：当前节点/分支、历史 messages、待确认的结构化参数、已执行的工具调用记录。生产用 MySQL。

- **[必答] 跨会话恢复的幂等性**：重放会不会重复预订？
  > 💡 **建议答法**：每个工具调用有**幂等键**（基于 thread_id + 操作类型 + 时间窗口生成），外部系统（腾讯会议 API）侧也做幂等检查；恢复执行时先查状态机里该工具是否已执行（有 tool result），已执行则跳过，不重发请求。

## 3. Human-in-the-loop 与会议纪要闭环

- **[必答] 审批阶段的自然语言改参**：怎么把"改到明天下午"合并到结构化参数？
  > 💡 **建议答法**：确认阶段有专门的"参数修订节点"——用 LLM 解析用户的自然语言修订意图，提取要变更的字段（如 date/time），与当前结构化参数合并（覆盖变更字段），再走一遍前置校验，然后重新展示给用户确认。不重走意图识别，只做参数级别的 patch。

- **[必答] 超长纪要分片与合并**：Map-Reduce 还是 Refine？分片依据是什么？
  > 💡 **建议答法**：用 **Map-Reduce 模式**（并行分片各自总结，再合并汇总），优于 Refine（Refine 是串行，前一段的误差会传递到后段）。分片依据：按 token 预算切分（保证每个分片 + system prompt 不超 context limit），优先在段落/发言人切换处断开。单段超 context：继续二次分片（递归处理）。

- **[常问] 异步发送机制**：如何保证投递可靠性？
  > 💡 **建议答法**：纪要生成后入消息队列（or 数据库任务表），异步任务轮询发送，发送成功后标记完成；失败按指数退避重试；幂等键防止重复发送（以 meeting_id + date 为幂等键）。实际用的是数据库任务表 + 定时轮询。

- **[常问] 输出格式与模板化**：为什么要支持 Markdown/HTML/邮件模板？怎么保证不同渠道一致性？
  > 💡 **建议答法**：核心是“同一份结构化纪要，多渠道渲染”。先产出统一的结构化数据（议题/决策/行动项），再按模板渲染 Markdown/HTML/邮件；模板版本可回滚，避免格式变更影响用户阅读。

- **[常问] 腾讯会议 API 的限制与稳定性**：超时/格式异常/截断怎么处理？
  > 💡 **建议答法**：外部 API 不稳定是常态——设超时 + 重试（幂等接口才重试）；格式异常时解析兜底（用宽松解析 or 降级到原文）；转写文本截断时和分片逻辑配合（先检测长度再决定分片策略）。

## 4. 幻觉治理与 API 兼容

- **[必答] "提取参数补执行"是怎么做的？**
  > 💡 **建议答法**：检测到幻觉（声称成功但 message 里无 tool_calls）→ 从**上下文的对话历史**里用规则提取参数（优先规则，稳定快速）；规则提不到时用 LLM 语义提取（兜底）→ 用提取的参数重新发起工具调用。补执行成功率约 85%。重点：补执行有幂等保护，不会重复创建。

- **[必答] 幻觉检测判断标准**：如何区分"真的调了但没结果"和"根本没调"？
  > 💡 **建议答法**：检测顺序：① 检查 message 对象里是否有 `tool_calls` 字段（最可靠，API 级别）；② 有 tool_calls 但工具返回 error → 是调了但失败；③ 没有 tool_calls 但 content 里声称"已创建" → 是幻觉。规则优先，LLM 语义检测作为兜底（检测模型输出里的"成功类"表述）。

- **[常问] 序列修复与安全截断**：消息序列有什么限制？截断策略是什么？
  > 💡 **建议答法**：DeepSeek 等模型要求 tool_calls 和 tool result 必须配对（有 tool_calls 的 assistant message 后面必须跟对应的 tool message）；截断时用**保头尾策略**（system prompt 和最近 N 轮对话保留，丢弃中间的旧轮次），保留完整的 tool_calls/tool_result 配对（不能只保留一半），否则 API 报序列不合法错误。

- **[必答] 成本下降怎么量化？**
  > 💡 **建议答法**：统计**同等用户操作量下**的 token 消耗：改造前（序列报错导致重试 + 幻觉漏执行用户重发）的 token 总量 vs 改造后。日均从约 120 万降到约 86 万，下降约 28%。口径：只统计正常业务流量（剔除测试调用）。

## 5. 把 AI Agent 当"工程系统"来问

- **[必答] 线上 SLA 与监控**：
  > 💡 **建议答法**：监控分层：① 工具调用成功率（区分幻觉/超时/参数错/外部拒绝）；② 意图路由准确率（有测试集定期回归）；③ 端到端任务完成率（用户目标达成）。失败归因：先看 tool_calls 是否存在，再看外部 API 状态，最后看序列合法性。

- **[必答] Prompt 注入与工具越权**：
  > 💡 **建议答法**：工具层做参数白名单校验（不信任 LLM 生成的参数，每个参数都经过格式/范围校验）；高风险操作必须经过 HITL 二次确认（即使 LLM 生成了正确参数，用户也要确认才执行）；会议 ID/用户 ID 从 session 上下文注入，不允许 LLM 自行生成（防止越权访问他人会议）。

- **[常问] 评测与回归**：回归集怎么建？
  > 💡 **建议答法**：收集真实对话样本（正常流程 + 边界场景 + 已知 bug 复现用例），标注预期的工具调用和最终结果；每次 Prompt 或模型版本变更后跑回归，关注幻觉率和意图准确率变化。测试集约 200 条，覆盖预订/纪要/查询等 6 类意图。

- **[加分] 可观测性与审计**：
  > 💡 **建议答法**：每步工具调用都记录日志（工具名/入参/出参/状态），脱敏后入库；LangGraph 的状态快照存 Checkpointer，支持回放指定会话的执行轨迹；可以 replay 到某个节点查看当时的 state，定位"哪步决策出错"。

## 6. 业务价值与合规

- **[必答] 为什么安全部门做会议 Agent？**
  > 💡 **建议答法**：安全部门对"留痕与合规"有天然的需求——会议预订记录、纪要留存、操作审批链路，和安全审计的核心诉求一致。同时这是内部效率工具（非面向外部），合规边界更清晰，是很自然的 AI 工程化落地场景。

- **[必答] 数据出境与脱敏合规**：
  > 💡 **建议答法**：调用外部大模型 API 前，对 prompt 中的 PII 做脱敏（人名→匿名标识，电话/邮件→屏蔽，内部项目名→通用描述）；会议内容/纪要文本只在内部系统留存，不传给外部 API 原文。有数据出境审批流程；长期计划私有化部署，现阶段公有云 API + 严格脱敏。

- **[常问] 用什么指标衡量好用？**
  > 💡 **建议答法**：任务完成率（用户发出意图到最终操作完成）、平均确认轮次（越少越好，说明意图理解准）、人工介入后修订率（用户在 HITL 阶段改参数的比例，高说明初次生成质量差）。
