# 02｜项目二：业务安全平台 3.0

> 微众银行 App 登录/转账风控、Flink 特征预计算、Redis 特征存取、CDC 配置下发、Shadow Mode、ClickHouse 明细、CEP 链式欺诈识别

## 0. 面试开场（30 秒讲法）

- **一句话结论**：我在不影响存量同步决策链路的前提下做**增量式重构**：引入 RocketMQ 事件流 + Flink 实时特征预计算，特征落 Redis，在线 API 走“取特征 + 规则计算”同步返回动作（放行/拦截/挑战），并把策略上线做成 Shadow Mode 可验证、决策明细可审计可追溯。
- **关键约束**：必须在“交易/登录前”同步出结果；时序特征需要事件时间语义；乱序/迟到不能把特征算错；新策略不能一上来就影响主链路（要影子验证）；链式欺诈要能解释“命中路径”。
- **落地结果**：对外同步决策接口 **P99 < 150ms**、日均调用量 **1000 万+**（监控口径）；新策略上线前可基于真实流量影子验证降低误拦；命中明细落库可审计、可回溯。

### 0.1 口径卡片（已预填简历已知信息，⚠️ 标注处需补填实际数据）

**卡片A：P99 < 150ms 口径（同步决策接口）**
- 指标名：微众银行 App 登录/交易风控**同步决策接口** P99
- 含义：请求进入风控到返回动作（放行/拦截/挑战）的端到端耗时（含 Redis 取特征 + 规则计算）
- 统计窗口：生产高峰时段/活动期（建议准备两组）
- 来源：APM/网关指标（说“APM/监控”，不报系统名）

**卡片B：日均调用量 1000 万+ 口径**
- 指标名：同步决策接口日均调用量
- 统计窗口：自然日

- 达标切换：误拦样本复核通过率 > 95%、“达标口径”（命中率在预期范围内，人工复核无重大异议）

### 0.2 事故复盘卡片（已预填思路，⚠️ 标注处补实际数据）

- **现象**：新策略影子验证阶段命中率异常偏高/偏低，或在线 P99 抖动，或 Flink 侧状态恢复后指标偏差
- **证据**：Flink 任务指标（Checkpoint 时长/失败次数/反压/延迟）、Redis 读写延迟、ClickHouse 明细抽样回放、APM 看在线接口 P99
- **根因**：常见根因：事件时间/水位线策略不合理导致窗口指标偏差；或 CDC 下发延迟导致规则版本不一致；或 Redis 热点导致取特征抖动
- **修复**：统一事件时间与水位线策略；Checkpoint 参数与 state TTL 调整；CDC 版本号与灰度发布；Redis 热点治理（本地缓存/分片/限流）
- **防回退**：把“影子命中率、误拦样本、在线 P99、Checkpoint 成功率”纳入发布门禁

## 1. 增量式重构：RocketMQ 事件流 + Flink 预计算 + Redis 特征存取

- **[必答] 为什么要做“增量式重构”，而不是推倒重来？**
  > 💡 **建议答法**：存量同步链路可用且风险高（金融链路不能频繁抖）；我们在不影响存量的前提下新增事件流与预计算链路，先把“时序特征/链式识别/影子验证/审计明细”补齐，再逐步把在线依赖从“多下游查询”收敛成“取特征 + 规则计算”，风险可控、收益可量化。

- **[必答] Flink 预计算到底算了什么？在线链路为什么会更快更稳？**
  > 💡 **建议答法**：把时序/窗口类特征前置到流式计算（Flink）做，落 Redis；在线请求只需要按 key 取特征 + 规则计算，不再同步扇出调用数十下游。在线链路从“依赖多→尾延迟敏感”变成“依赖少→可控”，更容易把 P99 压住（简历口径 P99<150ms）。

- **[必答] 在线取特征（Redis）怎么做？Key/TTL/一致性怎么取舍？**
  > 💡 **建议答法**：特征按用户/设备/卡/商户等维度建 key（不泄密只讲维度），TTL 与特征窗口一致；一致性上接受最终一致（少量延迟/乱序通过事件时间+水位线矫正），在线侧优先可用性与稳定延迟；关键是讲清“错一点点特征 vs 抖动整个交易链路”的取舍。

## 2. 事件时间/水位线/Checkpoint：如何保证特征不算错

- **[必答] 事件时间和水位线怎么定？为什么不用处理时间？**
  > 💡 **建议答法**：风控特征很多是窗口统计/时序指标，乱序/延迟如果按处理时间会算错；用事件时间 + 水位线可以把“允许迟到”的窗口语义讲清楚。关键是说明你怎么设 allowed lateness、窗口大小、以及迟到数据怎么补偿/修正。

- **[必答] Checkpoint 语义你怎么理解？怎么保证恢复后状态正确？**
  > 💡 **建议答法**：说清楚你们要的是哪种一致性（通常是 exactly-once 或 at-least-once + 幂等落库），Checkpoint 成功率/耗时如何监控；恢复后如何避免重复输出（幂等 key/下游去重）。

- **[常问] 反压（backpressure）出现时怎么处理？**
  > 💡 **建议答法**：先定界是 source/算子/下游 sink 哪一段慢；调并行度、优化算子、以及对 sink（Redis/ClickHouse）做批量/限速；必要时分层降级（先保证关键特征计算）。

## 3. 配置化与发布：Aviator 表达式 + MySQL CDC 下发

- **[必答] 规则表达式为什么选 Aviator？表达能力与边界是什么？**
  > 💡 **建议答法**：Aviator 足够表达大多数风控规则（阈值/布尔组合/函数），且配置化成本低；边界是复杂图算法/超重计算不适合放规则里（要预计算或专用服务）。

- **[必答] CDC 下发怎么保证版本一致性与可回滚？**
  > 💡 **建议答法**：规则有版本号/生效时间，CDC 下发到各节点后按版本切换；支持快速回滚到上一版本；灰度策略（先部分节点生效，观察命中与误拦样本）。

- **[常问] 策略调整为什么要“可审计”？你们怎么做审计留痕？**
  > 💡 **建议答法**：每次规则变更都有变更人/变更内容/版本号/生效范围记录；命中明细里带规则版本，支持事后追溯“当时为什么拦/放”。

## 4. Shadow Mode 与审计明细：ClickHouse 明细落库与回溯

- **[必答] Shadow Mode 怎么做？怎么用真实流量验证效果？**
  > 💡 **建议答法**：新策略默认不影响主链路动作，只产出命中明细；用真实流量统计命中率，并抽样做误拦样本复核；达标后再切换为生效策略。核心是“先验证，再放量”，避免误杀。

- **[必答] ClickHouse 明细里记录哪些字段/上下文？怎么支持审计追溯？**
  > 💡 **建议答法**：记录命中策略版本、命中路径（CEP 多步行为）、关键上下文（设备/IP/金额等类别字段，不泄密），支持按交易/用户回溯“为什么命中”。

- **[常问] Shadow Mode 到正式生效的切换怎么做灰度与回滚？**
  > 💡 **建议答法**：切换是配置化的，按规则版本灰度；回滚回到上一版本；关键是可审计（谁在什么时候把策略从影子切到生效）。

## 5. CEP 链式欺诈识别：命中路径可解释

- **[必答] CEP 怎么建模“多步行为序列”？窗口/状态约束怎么定？**
  > 💡 **建议答法**：举简历里那条链路例子（新设备/异地登录 → 改密 → 小额试探 → 大额转出），说清楚时间窗口、状态条件、以及命中后输出“命中路径 + 关键上下文”用于处置与复盘。

- **[常问] CEP 的状态膨胀怎么控制？**
  > 💡 **建议答法**：state TTL、按 key 维度做限界、超时清理；必要时对高基数 key 做采样或分层（不泄密讲机制）。

- **[加分] 命中路径怎么做“可审计/可追责”？**
  > 💡 **建议答法**：命中明细落 ClickHouse，带规则版本与路径；运营处置留痕；事后能回放“当时为什么命中”。

## 6. 可靠性：乱序/迟到/幂等与一致性校验

- **[必答] 乱序/迟到会不会影响特征与结论？你怎么处理？**
  > 💡 **建议答法**：事件时间 + 水位线 + allowed lateness；关键特征允许迟到补偿，迟到太多的走离线纠偏；把“可接受的误差/延迟窗口”讲清楚。

- **[常问] 数据重复（at-least-once）怎么做幂等？**
  > 💡 **建议答法**：消息/事件有唯一 key（不泄密讲“由业务字段组合”），下游落库/写 Redis 做幂等更新；必要时用版本号避免乱序覆盖新值。

- **[加分] Shadow 链路与主链路结果不一致怎么排？**
  > 💡 **建议答法**：ClickHouse 明细抽样回放 + 规则版本对齐 + 特征快照对齐，先排“版本不一致”，再排“迟到/乱序窗口语义”，最后排代码差异。

## 7. 指标口径自证（必须准备，考前对着念一遍）

- **[必答] P99 < 150ms 口径**：
  > 💡 **建议答法**：是同步决策接口的 P99，统计窗口是生产高峰/活动期；主动说清口径是否含“取特征 Redis + 规则计算”的全链路耗时；用 APM/网关指标佐证。

- **[必答] 1000 万+ 日均调用量口径**：
  > 💡 **建议答法**：自然日统计，剔除探活/拨测；均值 QPS 只是参考，峰值更关键（发薪日约 220 QPS）。

- **[必答] Shadow Mode 达标口径**：
  > 💡 **建议答法**：命中率只是表面，更关键是误拦样本（人工复核通过率/申诉率/回滚次数），达标后才切到生效策略；切换仍走灰度。

- **[常问] "生产环境无 P0/P1 事故"口径**：
  > 💡 **建议答法**：说清 P0/P1 定义标准；主动说有没有灰区（比如"降级成功但业务有损"的情况）；这类如实说反而更可信。
